01 / 一句话主线

先把三层关系讲清楚

框架层MindSpore计算图Primitive / Custom
⬇ 图编译、算子选择、shape/dtype 推导
平台层CANNACL / GE算子库编译器运行时
⬇ kernel 编译、launch、stream、memory
硬件层AI CoreCubeVectorScalarGM/UB/L1/L0

MindSpore 负责“图和训练语义”，CANN 负责“把算子落到昇腾硬件”，Ascend C/TBE 负责“写或生成具体 kernel”。

02 / 为什么要关心算子

深度学习模型最终会被拆成很多算子

模型视角

Conv、MatMul、Softmax、LayerNorm、Gather、Reshape、通信 op 共同构成网络。

编译视角

图优化会做融合、常量折叠、layout 转换、算子选择与 kernel 调度。

硬件视角

性能取决于数据搬运、并行切分、内存层级、Cube/Vector 利用率。

一个模型“能不能跑、跑得准不准、跑得快不快”，常常卡在少数关键算子：不支持、shape 动态、dtype 不匹配、融合失败、内存搬运过多。

03 / 昇腾硬件抽象

AI Core：不只是“GPU 的国产替代”

Cube 计算单元

面向矩阵乘 / 卷积等高吞吐张量计算，是大模型 GEMM、Conv 的核心。

典型瓶颈：tiling、layout、L0/L1 数据复用。

Vector 计算单元

面向 elementwise、激活、归一化、数据变换等向量操作。

典型瓶颈：UB 容量、访存连续性、流水并行。

Scalar 控制

负责标量计算、地址计算、循环控制与 kernel 调度逻辑。

存储层级

Global Memory 到 Local/Unified Buffer 再到计算单元，算子优化本质上是在减少慢速搬运。

04 / CANN 是什么

CANN：昇腾 AI 处理器的软件基础设施

模型/图MindSpore / ONNX / ATC
→
图引擎GE, graph optimization
→
算子与编译op library, TBE, Ascend C
→
运行时ACL, stream, memory
→
AI Coreexecute kernels
  • 开发者入口：ACL 应用开发、ATC 模型转换、Ascend C/TBE 自定义算子、Profiler 调优。
  • 框架入口：MindSpore 后端通过 CANN 调用算子库、编译器和运行时。
  • 核心价值：屏蔽硬件细节，同时保留高性能 kernel 开发通道。
05 / MindSpore 在哪里

MindSpore：用计算图组织训练/推理，再交给 CANN

前端表达

Cell / Tensor / ops / grad，把网络、损失和优化器组织成动态图或静态图。

图模式编译

Graph Mode 下做图优化、自动微分、并行策略、算子级并行、内存复用。

算子接口

内置 ops 覆盖常用深度学习算子；不足时可用 Custom 或 CustomOpBuilder 接入。

昇腾后端

把图中算子映射到 CANN 算子库或用户自定义 kernel，最终在 Ascend NPU 上执行。

06 / 算子从哪来

三类算子：能用库就别手写，必须手写再下沉

类别适合场景优点风险
内置算子Conv/MatMul/LayerNorm/Softmax 等常见 op稳定、性能好、被框架图优化识别新模型结构可能缺少特殊变体
组合算子用多个已有 ops 拼出功能开发快、可维护可能产生多次访存，融合失败会慢
自定义算子新算法、特殊 shape、融合 kernel、性能热点控制力强，可极致优化开发/调试/适配成本高

判断顺序：内置可用 → 组合可接受 → 图融合能解决 → 最后才写自定义算子。

07 / MindSpore 自定义算子入口

MindSpore 官方主要给两条路

Custom Primitive

  • 统一 Custom 原语，在算子执行阶段调用用户接口。
  • 支持 Graph Mode 与 PyNative Mode。
  • AOT 类型可接入预编译 so；Ascend 平台可接入自定义算子。
  • 调度流程更接近内置算子，性能路径更完整。

CustomOpBuilder

  • 在线编译和加载自定义算子模块。
  • 更偏 C++ tensor 编程，执行流程直观。
  • 主要用于 PyNative Mode，适合快速接入与验证。
  • 也可通过 Runner 接入 ATB / ACLNN 等算子。

来源：MindSpore master 教程“自定义算子”与 API 文档 Custom；接口等级和平台支持以安装版本文档为准。

08 / Ascend C 是什么

Ascend C：面向昇腾算子开发的 C/C++ 编程语言

C/C++ 风格

接近开发者既有习惯，入口函数用设备侧 kernel 表达。

结构化核函数

把搬运、计算、写回组织成清晰流程。

自动并行调度

通过 block、tiling、pipeline 让数据在 AI Core 上并行。

CPU/NPU 调试

可先在 CPU 仿真环境验证，再上 NPU 加速计算。

官方描述：Ascend C 是 CANN 面向算子开发推出的编程语言，原生支持 C/C++ 标准规范，算子经编译器编译和运行时调度后运行在昇腾 AI 处理器上。

09 / 一个 Add 算子的内核逻辑

写 kernel 前先做“算子分析”

数学表达式z = x + y
→
输入输出x, y → z
→
dtype / shapefloat16, shape range
→
数据流GM → UB → compute → GM
Global Memory: x, y │ copy in ▼ Local / Unified Buffer: x_tile, y_tile │ vector add ▼ Local / Unified Buffer: z_tile │ copy out ▼ Global Memory: z
10 / Ascend C 代码长什么样

HelloWorld 级别的 kernel 入口

#include "kernel_operator.h" extern "C" __global__ __aicore__ void hello_world() { AscendC::printf("Hello World!!!\n"); } void hello_world_do(uint32_t blockDim, void *stream) { hello_world<<<blockDim, nullptr, stream>>>(); }
  • __global__ __aicore__：声明运行在 AI Core 上的设备侧入口。
  • <<<blockDim, ..., stream>>>：类似 CUDA kernel launch，但面向昇腾运行时。
  • 真实算子会包含 tiling、队列、copy in / compute / copy out 等结构。
11 / 两种工程形态

Kernel 直调 vs 框架接入

Kernel 直调工程

先把 kernel 当成一个独立程序跑通：编译、CPU 模式验证、NPU 模式验证、性能 profiling。

适合学习、调试、微基准测试。

自定义算子工程

补齐 op 原型、shape/dtype 推导、注册信息、kernel binary，让框架图编译时可以识别和调度。

适合接入 MindSpore/模型生产流程。

不要一上来就接框架。先用 kernel 直调把数学正确性和性能基本盘跑通，再处理 MindSpore 注册与图编译问题。

13 / 算子性能的核心：tiling

tiling：把大张量切成硬件吃得下的小块

为什么要切

Global Memory 容量大但慢；本地 buffer 快但小。算子要把数据分块搬进本地，再尽量复用。

切什么

矩阵维度、batch、channel、sequence length、head、blockDim、每次搬运的 tile size。

切错会怎样

UB 放不下、访存不连续、计算单元等数据、并行粒度过小或过大。

调优目标

让搬运与计算重叠，让 Cube/Vector 尽量满，让中间结果少回 GM。

14 / 数据搬运比代码更重要

很多 NPU 算子慢，不是“算得慢”，而是“搬得慢”

低效模式GM 读 x → 算一点 → GM 写 tmp → 再读 tmp → 再写 y
⬇ 优化
高效模式GM 读 tile → UB 内多步计算 → 只写最终 y
  • 融合：把 elementwise + reduce + activation 合到一个 kernel，减少中间张量落 GM。
  • 双缓冲/流水：copy in、compute、copy out 并行推进。
  • layout：让访存连续，让硬件向量化/矩阵计算单元更容易吃满。
15 / 图编译与算子融合

框架层优化决定“你写的算子是否真的被用上”

Pattern Fusion

Conv+BN+ReLU、MatMul+Bias+Activation、LayerNorm 子图融合。

Op Selection

同一个算子可能有多个实现，根据 dtype、shape、format 选择 kernel。

Format Transform

NCHW/NHWC/NC1HWC0 等 layout 转换会成为隐藏成本。

做自定义算子时要问：它是替代单个 op，还是替代一个子图？是否破坏原本可以发生的融合？shape/dtype 推导是否足够让图编译器识别？

16 / 常见接入坑

自定义算子最容易卡在这些地方

1. shape/dtype 不完整

只测固定 shape，一到动态 batch 或边界长度就编译失败。

2. 精度对齐不严

float16/bfloat16/float32 累加策略不同，误差阈值要按算子性质设置。

3. 注册信息缺失

框架不知道输入输出、format、target、kernel 名称，图编译无法选择。

4. 性能只看单 kernel

单算子快了，但前后 layout 转换增加，端到端反而慢。

17 / 调试工具链

先证明“算对”，再证明“跑快”

CPU 仿真

非昇腾设备也可先安装 CANN，用 CPU 仿真环境开发与测试 kernel 逻辑。

Dump / 日志

定位图编译、shape 推导、精度差异和中间张量异常。

Profiler

看 kernel 时间、AI Core 利用率、stream 并行、内存搬运、通信等待。

调试顺序：最小 shape → 多 shape → 随机输入 golden → 极值输入 → 端到端模型 → profiler。

19 / 大模型里的高频算子

LLM 在昇腾上优化，常围绕这几类热点

GEMM / MatMul

QKV、MLP、投影层；Cube 利用率是关键。

Attention

Softmax、mask、KV cache、FlashAttention 类融合。

Norm / Activation

LayerNorm/RMSNorm/SwiGLU；常见融合目标。

通信与并行

AllReduce、AllGather、ReduceScatter 与计算重叠。

真实性能优化不是“写一个更快的 op”这么简单，而是算子、图融合、并行策略、通信和内存共同优化。

20 / 什么时候该写自定义算子

一个实用决策树

模型在昇腾上有问题？ │ ├── 直接不支持 / 编译失败 │ ├── 能用等价内置 op 改写？ → 先改模型图 │ └── 不能 → 自定义算子 / 等待官方支持 │ ├── 能跑但很慢 │ ├── profiler 显示单个 op 热点？ → 评估融合或手写 kernel │ ├── layout transform 很多？ → 优先改 format / 图融合 │ └── 通信等待多？ → 优先并行策略与通信重叠 │ └── 精度不一致 ├── dtype / cast / 累加策略问题？ → 调整数值路径 └── kernel bug？ → golden + dump 定位

输入

计算

输出

22 / 工程 checklist

上线前检查清单

功能正确

  • 覆盖 dtype、shape、动态 batch、极端输入。
  • 有 golden test 和误差阈值说明。
  • CPU 仿真和 NPU 实测都通过。

性能可信

  • 有与内置/组合实现的端到端对比。
  • Profiler 解释瓶颈，不只报单个数字。
  • 确认没有引入额外 layout transform。

框架接入

  • 注册信息、shape/dtype 推导、target 支持完整。
  • Graph/PyNative 支持范围清楚。

可维护

  • 写明 CANN/MindSpore/驱动版本。
  • CI 覆盖编译、单测、模型 smoke test。

24 / 总结

把“算子开发”放回整条 AI 软件栈里理解

MindSpore

负责模型表达、自动微分、图优化、并行与自定义算子接口。

CANN

负责图引擎、算子库、编译器、ACL 运行时、Profiler 与昇腾硬件连接。

Ascend C

负责把关键计算写成高性能 AI Core kernel，处理搬运、tiling 与并行。

核心判断：先用框架和内置算子解决 80%，再针对瓶颈算子用 Ascend C 做 20% 的深度优化。
