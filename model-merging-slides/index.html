模型合并 Model Merging：
不用重新训练,能不能把多个模型能力拼起来?

从 Model Soups 到 Task Arithmetic,从 TIES/DARE 到 mergekit 与进化搜索。

核心问题
多个 fine-tuned models / LoRA / checkpoints 能否在参数空间直接组合?
工程价值
省训练、省数据、省显存,把已有模型资产复用成新能力。
主要风险
能力冲突、灾难性遗忘、安全与版权边界不清。

调研数据: OpenAlex + arXiv,10 组关键词,筛得 100 条相关候选；本 deck 选取 15 条代表路线讲解。

学习目标

1. 看懂直觉

为什么两个模型的参数可以平均? 什么时候平均会失败?

2. 掌握路线

checkpoint averaging, task vector, importance-aware, sign conflict, LoRA/adapters。

3. 会选方法

给定“同基座/不同任务/无数据/多 LoRA”场景,知道用哪类 merge。

4. 看到机会

理解自动配方搜索、多模态 merge、安全评估等研究机会。

一句话定义

θmerged = Merge(θbase, θ1, θ2, ..., recipe)

输入

同一基座微调出的多个模型,或多个 checkpoint / LoRA / adapter。

操作

在参数、delta、神经元、特征或 adapter 空间做组合。

输出

一个尽量保留多模型能力、无需全量重训的新模型。

关键前提: 多数有效方法默认模型来自同一 base,且参数语义大体对齐。

为什么突然重要?

Foundation Model→SFT / RLHF→领域模型→模型资产池→合并复用

训练成本高

大模型全量重训昂贵,但微调模型/LoRA 越来越多。

数据不可共享

公司/实验室可能只有模型权重,没有原训练数据。

能力碎片化

代码、数学、医疗、中文、工具调用分别强,希望拼成一个。

社区可复现

mergekit 等工具让模型合并成为低门槛实验范式。

发展脉络：从平均 checkpoint 到自动配方搜索

2017-2018FedAvg / SWA: 参数平均与训练轨迹平均
2021-2022Fisher / Model Soups: 重要性加权与同 basin 平均
2022-2023Task Arithmetic / RegMean: task vector 与闭式层合并
2023-2024TIES / AdaMerging / DARE: 冲突消解、自适应权重、稀疏 delta
2024-2026mergekit / evolutionary recipes / LoRA fusion: 工程化与自动化

方法地图：模型合并不是一种算法,而是一组操作空间

参数空间

linear averaging, greedy soup, SLERP, Fisher weighting。

Delta 空间

task vector, TIES, DARE, breadcrumbs, sign election。

结构/特征空间

neuron matching, feature alignment, ZipIt, layer-wise merge。

Adapter 空间

LoRA / adapter composition, K-LoRA, weighted adapter merge。

优化空间

AdaMerging, entropy minimization, validation-free weighting。

搜索空间

mergekit recipes, evolutionary search, model stock。

前提条件：什么时候“能合并”?

条件为什么重要失败表现
同一 base model参数位置语义一致不同架构直接平均通常崩溃
线性模式连接两个解之间存在低 loss 路径平均点 loss 高,能力同时下降
任务冲突有限delta 方向不要大面积相反A 能力增强同时 B 能力遗忘
尺度/归一化一致权重范数、LayerNorm 统计要兼容输出分布漂移,生成质量下降

基线 1：Linear Averaging / Checkpoint Averaging

θ = α θA + (1-α) θB

优点

  • 最简单,无需数据
  • 对同一训练轨迹/同一任务很稳
  • 可作为所有 merge 的 sanity check

局限

  • 多任务冲突时容易互相抵消
  • 不同 fine-tune recipe 可能不在同一 basin
  • 无法解释哪些参数该保留

代表作：Model Soups (ICML 2022)

核心做法

把同一预训练模型上不同超参数微调出的多个模型做权重平均。Uniform soup 直接平均；Greedy soup 按验证集表现逐个加入。

关键启发

大模型 fine-tuning 的多个好解常位于同一个低损失盆地,平均后泛化可能更好。

base→fine-tune variants→filter good models→average weights→better generalization

代表作：Task Arithmetic (ICLR 2023)

τtask = θtask - θbase
θnew = θbase + ατA + βτB - γτbad

为什么重要

把“任务能力”表达成参数差值向量,可以做加法、减法、组合。

直觉

fine-tuning 不只是得到新模型,还留下了一条从 base 指向任务能力的向量。

Task Vector 的问题：冲突与冗余

符号冲突

同一个参数上,任务 A 希望增加,任务 B 希望减少。简单相加会抵消或破坏两边。

幅度冲突

少数大 delta 可能主导合并,小任务被淹没。

冗余参数

很多 delta 对能力贡献很小,全量合并反而引入噪声。

任务相关性

相近任务可叠加,相斥任务需要路由或分专家。

代表作：TIES-Merging (NeurIPS 2023)

Trim→Elect Sign→Disjoint Merge
步骤含义解决的问题
Trim只保留 magnitude 较大的 delta去掉冗余噪声
Elect Sign为每个参数选多数/强势方向减少符号冲突
Merge只合并同方向 task vector保留多任务能力

代表作：DARE (2024)

Drop + Rescale task vectors

做法

随机丢弃 task vector 中大量参数,再按保留比例重标定,然后执行合并。

发现

很多微调 delta 高度冗余;保留少量关键变化也能维持任务能力。

工程上常见组合: DARE + TIES,先稀疏化再做符号冲突消解。

代表作：AdaMerging (ICLR 2024)

问题

如果没有训练数据/验证集,怎么给不同任务模型分配合并权重?

方法

使用测试时熵最小化等无监督目标,学习 task-wise / layer-wise merge coefficients。

多个 task vectors→可学习权重→无监督目标→adaptive merged model

代表作：RegMean / Fisher / Importance-aware Merge

方法核心信号适用场景
Fisher mergingFisher information 表示参数重要性有少量数据/可估计重要性时
RegMean线性层输入协方差,闭式求解合并权重多任务模型,层级输出对齐
Layer-wise weights不同层分配不同 α低层共享、高层任务特异明显时

直觉: 不是每个参数都同等重要,合并要“少动关键参数,多动可塑参数”。

代表作：ZipIt! 与结构对齐

为什么需要对齐?

两个网络即使功能相似,通道/神经元排列也可能不同。直接平均会把不对应的特征混在一起。

ZipIt! 思路

先根据 feature similarity 对齐/匹配内部表示,再压缩或融合网络。

这条路线提醒我们: 参数位置不是天然语义坐标,尤其在不同训练轨迹或结构变化下。

LLM 工程路线：mergekit 把方法变成 recipe

支持算子

linear, SLERP, task arithmetic, TIES, DARE, passthrough, layer slicing 等。

核心价值

用 YAML 明确写出 base、sources、权重、层范围、dtype,让合并可复现。

models:
  - model: base-or-instruct-A
    parameters: {weight: 0.55}
  - model: math-or-code-B
    parameters: {weight: 0.45}
merge_method: ties
dtype: bfloat16

SLERP：为什么社区喜欢球面插值?

SLERP(θA, θB, t) = spherical interpolation

线性插值的问题

高维权重向量范数可能变化,中间点分布不稳定。

SLERP 的直觉

沿球面保持方向/范数更平滑地从 A 走向 B,常用于两个 LLM 的温和融合。

LoRA / Adapter 合并：轻量模型资产的复用

base model+LoRA A+LoRA B→merged adapter / fused model

优势

文件小,组合快,不用保存多份全量模型。

难点

rank、scale、目标模块不同,多 LoRA 风格/能力会冲突。

代表方向

K-LoRA 等训练自由 subject/style 融合; weighted adapter merge。

自动化路线：Evolutionary Model Merge

人工 recipe 的问题

模型组合、层范围、权重、方法选择形成巨大搜索空间,手调成本很高。

进化搜索

把 recipe 当作个体,用基准测试得分做 fitness,通过 mutation/crossover 找更优合并配方。

model pool→recipe population→evaluate→mutate→best merge

场景决策树：该用哪种合并?

你的模型是什么关系?
│
├── 同一任务 / 同一训练轨迹
│   └── checkpoint averaging / SWA / Model Soup
│
├── 同一 base, 不同任务 full fine-tune
│   ├── 有验证集 → greedy soup / learned weights
│   └── 无数据   → task arithmetic + TIES / DARE
│
├── 多个 LoRA / adapter
│   └── weighted adapter merge / LoRA fusion / K-LoRA
│
└── 不同架构或不同 tokenizer
    └── 不建议直接 merge;考虑蒸馏、MoE 或路由

评估指标：不能只看一个 leaderboard 分数

维度要测什么例子
保留能力各源模型擅长任务是否还在Math, Code, Chinese, Domain QA
通用能力是否牺牲基础语言/视觉能力MMLU, GSM8K, HumanEval, MT-Bench
冲突能力两个能力同时触发时是否混乱中文数学代码题,多约束生成
安全性拒答、幻觉、越狱、隐私泄露SafetyBench, AdvBench, red-team prompts

常见误区 1：合并 ≠ 免费变强

错误说法

“把几个强模型一平均,就会得到全能模型。”

更准确

合并只是在已有能力之间做低成本重组,成功依赖同基座、低冲突和正确配方。

错误做法

只报告 merged model 的最高榜单,不测每个源能力是否遗忘。

更准确

必须报告 per-task retention、平均性能、最差任务和安全回归。

常见误区 2：不同模型都能合

不能直接合

  • 不同架构
  • 不同 tokenizer / vocab
  • 不同 hidden size
  • 不同参数命名或模块语义

替代方案

  • 知识蒸馏
  • Mixture-of-Experts 路由
  • Adapter composition
  • 输出级 ensemble

代表工作总览 1/2

年份工作关键词意义
2017Federated Averaging分布式/联邦场景的参数平均基础范式不是今天 LLM merge 的直接起点,但提供了 weight averaging 的统计直觉
2018SWA: Stochastic Weight Averaging单任务训练轨迹中的权重平均解释为什么“平均参数”有时比单点模型泛化更好
2021Fisher-weighted averaging用 Fisher 信息估计参数重要性从 naive averaging 走向 importance-aware merge
2022Model Soups把同一预训练模型微调出的多个模型做权重平均证明大模型微调结果常处在可连接低损失区域
2022Editing Models with Task Arithmetic把微调差值看成 task vector让“加技能/减偏见/组合任务”变成向量运算
2023RegMean从线性层输入协方差角度做闭式合并比简单平均更适合多任务模型融合
2023TIES-Merging解决 task vector 的符号冲突和冗余参数成为 LLM 多能力合并的经典强 baseline
2023AdaMerging不访问训练数据,只用测试时熵最小化学习合并权重把 merge 从固定配方推进到 data-free adaptive weighting

年份工作关键词意义

2024DAREDrop And REscale task vectors意外发现 task vector 高度冗余,常与 TIES 组合

模型合并与 MoE / Ensemble / Distillation 的区别

方法推理成本是否产生单模型是否需要数据典型用途
Model merging≈ 单模型是可无数据低成本组合能力
EnsembleN 倍否不需要训练数据提高稳定性/准确率
Distillation≈ 单模型是需要生成/训练数据压缩多个 teacher 能力
MoE / Router取决于激活专家是通常需要训练任务冲突大时分专家处理

研究机会 A：安全可控的模型合并

问题

合并可能削弱拒答、安全对齐或引入源模型后门。

技术路线

安全 task vector 分离;合并前后 red-team;对拒答能力加约束。

可发点

现有 merge 论文多看能力榜单,系统安全评估仍不足。

研究机会 B：多模态模型合并

问题

Vision encoder、LLM backbone、projector 三部分变化不同步。

技术路线

分模块 merge; projector 对齐;视觉/语言任务分别保持。

可发点

VLM/agent 模型越来越多,但 merge 仍主要集中在 LLM 文本能力。

研究机会 C：面向小团队的模型资产管理

问题

团队会积累大量 LoRA、领域 SFT、checkpoint,缺少“怎么组合”的方法。

技术路线

model card + eval matrix + recipe search + rollback。

工程产物

把 mergekit、评测脚本、模型注册表做成可复现流水线。

最小可跑实验设计

# 1. 选择同一 base 的 2-3 个模型
base = "mistral/llama/qwen base"
models = ["code-finetune", "math-finetune", "chinese-finetune"]

# 2. 先做 baseline
linear → slerp → ties → dare_ties

# 3. 每个 merged model 测 4 类任务
source tasks + general tasks + conflict tasks + safety tasks

# 4. 记录 recipe, seed, dtype, commit hash

原则: 先小模型/小评测闭环,再扩大到 7B/14B/多 LoRA。

实践 Checklist

合并前

  • 确认同 base / tokenizer / architecture
  • 收集源模型能力矩阵
  • 决定是 full-weight 还是 LoRA merge

合并中

  • 从 linear / SLERP baseline 开始
  • 再尝试 TIES / DARE / layer-wise weights
  • 保存 recipe 与随机种子

合并后

  • 测每个源任务 retention
  • 测通用能力和安全回归
  • 记录失败 recipe,避免重复踩坑

上线前

  • 灰度测试
  • 人工抽样
  • 回滚源模型

结论：模型合并的三句话

第一句: 模型合并的本质是“参数空间里的能力重组”,不是魔法增强。
第二句: 成功的关键是同基座、低冲突、好配方、完整评估。
第三句: 未来最有价值的方向不是再发明一个平均公式,而是自动配方搜索、安全约束、多模态与模型资产管理。

Q&A

模型合并真正难的不是“怎么平均”,而是如何知道哪些能力该保留、哪些冲突该牺牲、哪些风险必须回归测试。
