桌面搜索 25 年：从 Google Desktop 到 AnyTXT

2004Everything 发布 (David Carpenter) — 直接读 NTFS Master File Table，几秒建好 TB 级文件名索引。开源，不索引内容。
2004–2011Google Desktop 横空出世又黯然退场，证明了"全文索引"是刚需，但商业上不可持续。
2007DocFetcher (开源) — Java + Apache Lucene，桌面全文搜索的事实标准。但启动慢、内存大、Java 体验重。
2010sRecoll (开源，C++ + Xapian) — 跨平台、文档处理插件齐全，但配置复杂。
2014Listary — 提升 Everything 的快捷调用体验，但本身不建索引。
2017–AnyTXT Searcher 出场 — 把 Lucene/Xapian 的能力塞进 ~30MB 的单文件 EXE，主打"快、对中文友好、开箱即用"。
2020sAI 加持的语义搜索入场 (如 RAG + 向量库)，但 关键词全文 仍是桌面场景最低成本、最高精度的方案。

关键差异：文件名 搜索 vs 文件内容 搜索

Everything 类 (文件名)

  • 数据源：NTFS Master File Table (MFT)。
  • 索引：仅 filename → path。
  • 速度：1 秒建百万文件索引。
  • 代价：不能搜 PDF 里的"机器学习"四个字。

AnyTXT 类 (全文内容)

  • 数据源：打开文件、抽文本、拆词、入索引。
  • 索引：term → posting list (doc_id, positions)。
  • 速度：亚秒级查询，索引需数十秒到数分钟。
  • 代价：要解析格式、要监听变化、要压缩、要打 OCR。

一个比喻：Everything 是通讯录；AnyTXT 是把通讯录上每个人的聊天记录都读了一遍再编的索引。

整体架构：四层模型

UI 层 → 搜索引擎层 → 索引层 → 资源层 (文件解析 + 监听) → Windows FS / NTFS

UI 层

  • 主界面：搜索框 + 结果列表 (高亮命中片段)。
  • HTTP Search Service：http://127.0.0.1:port/...。
  • 系统托盘 + 全局快捷键 + 资源管理器右键。

搜索引擎层

  • 查询解析：分词 + 操作符 (AND/OR/NOT/phrase/regex)。
  • 查询计划：term → postings → 合并 (DAAT/TAAT)。
  • 评分：BM25 打分 + 字段加权 (title vs body)。
  • 高亮：把命中位置回填原文，标黄。

索引层

  • 倒排索引：词典 + postings list (含位置)。
  • 文件元数据表：path / size / mtime / doc_id。
  • 增量更新：merge 段 (segment)，定期合并。
  • 压缩存储：VB / Frame-of-Reference / PForDelta。

资源层

  • 解析器工厂：extension → 具体 Parser。
  • PDF / Office / eBook / OCR 各一个 Parser。
  • 文件系统监听：NTFS USN Journal / ReadDirectoryChangesW。
  • 线程池：解析 / 索引 / 监听 三类 worker。

数据流：扫描 → 解析 → 入索引

整个流程在 worker 线程跑；UI 线程只读索引、显示结果。两边通过内存里的一份倒排 + 一份段文件 (segment) 通信。

进程与线程模型

主进程 (UI)

  • 渲染窗口、响应键盘、处理设置。
  • 只读 索引；不参与解析。
  • 通过共享内存 / mmap 读取 segment 文件。

Index Worker (N 线程)

  • 文件 I/O + 解析 + 写索引。
  • 向 segment 追加新条目 (write-once)。
  • 优先级：先解小文件、再解大文件。

FS Watcher (1 线程)

  • 监听 NTFS USN Journal / RDC。
  • 把变更 (create / modify / delete) 推入任务队列。
  • 对二进制 / 临时文件做白名单过滤。

Segment Merger (后台)

  • 定期把小段合并成大段 (类似 LSM-tree)。
  • 删除已 remove 的 doc_id。
  • 索引空闲时触发，不阻塞查询。

这个结构和 Elasticsearch 的 Indexing Node + Coordinating Node + Merge 是同构的，只是单进程版。

倒排索引：搜索引擎的心脏

把"文档 → 词"的正向关系，反向 成"词 → 文档列表"。

正向索引 (Forward Index)

D1 → [机器, 学习, 是, ...] D2 → [深度, 学习, 改变, ...] D3 → [学习, 笔记, ...]

查"机器"需要遍历所有 D_i。

倒排索引 (Inverted Index)

机器 → [D1, D3, D42, ...] 学习 → [D1, D2, D3, D7, ...] 深度 → [D2, D5, D19, ...] ...

查"机器"：O(1) 跳到 term 槽，读 postings。

两段构成：① 词典 (dictionary / term dictionary) ② 倒排表 (postings list)。

Record-level vs Word-level 索引

Record-level (文档级)

postings 只存 doc_id；不记录词在文档中的位置。

学习 → [D1, D2, D3, D7]
  • 省空间：~30% 体积。
  • 缺点：无法支持 phrase query ("机器 学习" 紧邻)。
  • 缺点：无法精准高亮。

Word-level (词项级) ⭐ AnyTXT 用的

每个 posting 存 doc_id + 词位置数组。

学习 → [ D1: [3, 18, 92], D2: [5, 21], D7: [12, 44, 88, 200], ]
  • 支持 phrase / proximity 查询。
  • 支持高亮 (回填原文找上下文)。
  • 代价：占用 2-3× 空间，需压缩。

词典 (Term Dictionary)

通常用 FST (Finite State Transducer) 压缩，前缀共享，O(1) 查找 + 范围扫描。

Postings 压缩

doc_id 取 delta，position 也 delta；VB / Frame-of-Reference / PForDelta 编码，原始占用压到 1/5-1/10。

BM25 评分公式：1970s 的经典到 2020s 还在用

BM = Best Matching，1994 年 Okapi 系统提出，事实上的行业标准，比 TF-IDF 更稳。

给定查询 Q (含 term q1..qn)，文档 D 的 BM25 得分： score(D, Q) = Σᵢ IDF(qᵢ) · f(qᵢ, D) · (k₁ + 1) ─────────────────────────── f(qᵢ, D) + k₁ · (1 - b + b · |D|/avgdl) 其中： f(qᵢ, D) = term qᵢ 在文档 D 中的词频 |D| = 文档 D 的长度 (词数) avgdl = 整个语料库的平均文档长度 k₁, b = 自由参数，常用 k₁ ∈ [1.2, 2.0]，b = 0.75 IDF(qᵢ) = ln( (N - n(qᵢ) + 0.5) / (n(qᵢ) + 0.5) + 1 ) N = 总文档数 n(qᵢ) = 包含 qᵢ 的文档数

BM25 的核心直觉：词频饱和(出现 100 次不应该是出现 1 次的 100 倍有用) + 文档长度归一(短文档的"出现"更有信号)。

为什么 BM25 比 TF-IDF 更稳？

TF-IDF 的问题

  • 词频项是 线性：tf(t,d) × idf(t)。
  • 同样出现 10 次，对长文档 = 1% 占比，对短文档 = 50% 占比，长文档被严重低估。
  • 没有对文档长度做归一化 → 长 doc 吃亏。

BM25 的两项修正

  • 饱和函数：高频词收益递减。k₁ + 1 限制上限。
  • 长度归一：|D|/avgdl 出现后，长文档被适度补偿。
  • 参数 b 控制归一强度 (b=0 完全不归一，b=1 完全归一)。

中文分词：英文分词 + CJK 二次分词

英文侧 (容易)

输入: "Machine learning is fun." 分词: [machine, learn, is, fun] 处理: 停用词 (is, a, the) 过滤 归一: lower-case + Porter stemmer (learn → learn, learning → learn)

中文侧 (难点)

输入: "机器学习改变世界" 分词: [机器, 学习, 改变, 世界] # 词典分词 或: [机器学习, 改变, 世界] # 二元/新词识别 混合: [machinelearning, 改变, 世界] # 中英混排

常用方案：最大正向匹配 (FMM)、Jieba / IK Analyzer、n-gram 兜底。

AnyTXT 的"Multi-language (include Chinese, Japanese, Korean)" 说明它 至少维护一份中英混合词表 + CJK 二元分词兜底。

文件系统监听：NTFS 的杀手锏 USN Journal

NTFS 的 Change Journal (USN Journal) 是一个 append-only 的元数据变更日志：每条记录 = "哪个 MFT 记录、什么时间、改了什么"。

# USN_RECORD_V2 (简化版) struct USN_RECORD { uint32_t record_length; uint64_t file_reference_number; # 哪个文件 (MFT entry) uint64_t parent_file_reference_number; # 父目录 uint32_t file_attributes; # 创建/删除/重命名/写入... int64_t timestamp; wchar_t file_name[]; # 文件名 # 注意：不包含文件内容 (这是和 Everything 的共同点) }

USN Journal 的好处

  • 读 1 次 ioctl 就拿到全盘所有变更。
  • 不轮询、不遍历目录、CPU 几乎为 0。
  • Window 化的子集读取：FSCTL_READ_USN_JOURNAL。

对 AnyTXT 的含义

  • 检测到 file_attributes & FILE_NOTIFY_CHANGE_LAST_WRITE → 触发重新解析 + 重写 posting。
  • 检测到 FILE_ACTION_REMOVED → 标记 doc_id 失效，merge 时清理。
  • 对 FAT/exFAT 无 USN：fallback 到 ReadDirectoryChangesW。

文件解析器：插件式架构 (像 Apache Tika)

Parser 抽象

interface Parser { bool matches(path, ext, magic) # 是不是我吃的格式 Text extract(file) # 抽成 (text, metadata) string name() # 自报家门 } type Text { body string title string lang string # zh / en / ja / ko meta map # 作者/页数/创建时间... }

ParserFactory 决策

  • ① 魔数 (magic bytes)：前 N 字节判断真格式 (e.g. %PDF)。
  • ② 文件扩展名：快速分发。
  • ③ MIME sniff：fallback。
  • 特殊格式注册 OCR、密码解压等子链。

关键格式解析：PDF / DOCX / PPTX 怎么读？

📄 PDF

  • 解析 CMap 表 (ToUnicode) 解中文乱码。
  • 遍历 content stream 拼文字，保留位置。
  • 扫描件：先 render → image → Tesseract OCR。
  • 加密：先尝试空密码 / 用户密码，失败跳过。

📝 DOCX (OOXML)

  • 本质是 ZIP + XML。
  • 读 word/document.xml 提段落 + 表格。
  • 处理 w:tab、w:br 标签。
  • 嵌入式图片 → 单独入 OCR 链。

📊 XLSX / PPTX

  • XLSX：每个 sheet 一个 XML，逐 cell 取值 + 公式结果。
  • PPTX：每个 slide 一个 XML，遍历 shape/textbox。
  • 共享字符串表去重 sharedStrings.xml。
  • 大小：通常 1-50 MB，解析可秒级。

AnyTXT "without installing any other software" 意味着这些 Parser 都是 内嵌进 EXE 的，没有外部 LibreOffice / pdftotext 依赖。

编码检测 + 多语言 OCR

文本编码检测 (chardet / ICU)

  • 统计字节分布 + BOM (UTF-8/16/32)。
  • 中文：GBK / GB18030 / Big5 概率排序。
  • 日韩：EUC-JP / Shift-JIS / EUC-KR。
  • 兜底：UTF-8 强解 + 容错。

OCR 链路 (Multilingual OCR)

image bytes ↓ 1. 预处理 (去噪/二值化/校正) ↓ 2. Tesseract LSTM (eng + chi_sim + jpn + kor) ↓ 3. hOCR 输出 (带 word box) ↓ 4. 拼回原文 + 记录位置 ↓ 5. 入索引 (与 PDF 文本同质)

OCR 一次扫描件 100-500ms；意味着"扫描 1 万份纸质合同" 入库的瓶颈不在 IO，而在 OCR 算力。

性能优化 ①：Postings 压缩

postings 占了索引的 90% 体积。直接存 doc_id / position 数组太浪费，必须压缩。

3 个常用编码

  • VB (Variable Byte)：每个字节用 7 bit 存数据 + 1 bit 续接标志。最简单、CPU 快。
  • Frame-of-Reference (FOR)：每 128 个数取一个 block，统一减 block min。
  • PForDelta：每 128 个数选 90% 覆盖的 b bit，余下当异常值。压缩比最高。

为什么 postings 好压缩

  • doc_id 严格递增 → delta 远小于原值。
  • 位置增量小 (大部分 1-5)。
  • 有 聚集性：相关 term 集中在少数 doc。
# 假设 postings: [3, 17, 29, 30, 200, 201] # 原值大小: 6 × 4 byte = 24 byte # delta: [3, 14, 12, 1, 170, 1] → max=170, 需 8 bit # VB 编码: 每个值平均 1-2 byte → 压缩到 ~10 byte (2.4×) # PForDelta + 异常槽 → 压缩到 ~7 byte (3.4×)

性能优化 ②：mmap + 异步 I/O

mmap (内存映射)

segment_file = open("_0.pos") data = mmap(segment_file) # 操作系统按需 page-in postings = data[offset:offset+len] # 进程退出时自动 sync 写回
  • 查询时像访问内存一样访问磁盘。
  • OS 自动按 4KB page 调度，冷数据不占 RAM。
  • 多进程共享：多个 AnyTXT 实例同时 mmap 同一文件。

异步 I/O + SSD 优化

  • 解析 / 写索引 / OCR 全部走线程池，不阻塞 UI。
  • "SSD Optimization" = 减少 random read、写批量化 (一次 fsync 多个 segment)。
  • 任务优先级：小文件先、大文件后台。
  • 限速：避免把磁盘 IO 跑满造成系统卡顿。

"almost in 1 second" 这个宣称，本质是：mmap 让查询访问已缓存的 page，没有 read() 系统调用路径。

查询时加速：Skip List + DAAT 合并

# 短语查询 "机器 学习" — postings 求交 + 位置相邻 机器: [D1@3, D3@10, D7@5, D12@2, ...] 学习: [D1@18, D3@11, D5@1, D7@6, ...] ↑ 倒排拉链合并 (DAAT: Document-at-a-Time) phrase 匹配: 在 D1 里 "机器"@3 之后 "学习"@4 → 命中 ✓ (用 position list 的差 1 判定相邻) 加速技巧: postings 末尾加 skip pointer (每 √N 个元素一个) 机器: D1 ─┐ D3 │ D7 ├─ skip ──→ D7 (跳过 D3-D6) D12│ ...

skip pointer 让两个长 postings 求交时，O(N+M) → O(N·log(M) + M·log(N))。

扩展能力：HTTP / AES256 / Keyword View

HTTP Search Service

GET /api/search?q=机器学习&top=10 → JSON 响应: { "total": 137, "hits": [ {"path":"D:\papers\ml.pdf", "score":8.42, "snippet":"...机器学习改变..."}, ... ] }

开启后本地任何 HTTP 客户端 (浏览器 / curl / IDE 插件) 都能调。

AES256 索引加密

  • 索引文件 segment 落盘前用 AES-256-GCM 加密。
  • 密码派生：PBKDF2 / Argon2。
  • 内存里 mmap 的是明文 (但进程退出后只剩加密文件)。
  • 适用：涉密电脑、合规审计、防取证恢复。

Keyword View (关键词视图)

  • 从结果页"反向"列出命中文件的全部关键词。
  • 适合：拿到一篇陌生 PDF 时快速看其主题词。
  • 实现：doc_id → 该 doc 的 distinct terms，按 tf 排序取 top-K。

SSD Optimization

  • 合并写：N 个小 append 攒一次 fsync。
  • 避免：随机 seek、随机写小文件。
  • 冷数据：旧 segment 压缩率更高、读更少。

5 条工程教训

  1. 单文件 EXE也能做"小而全"——避免分布式复杂度。
  2. 用操作系统给的钩子（USN Journal）而不是自己轮询。
  3. mmap + 不可变段 = 亚秒级启动 + 实时一致性。
  4. 插件式 Parser = 30 个格式不写 30 套解析流程。
  5. AES + HTTP Service 把本地工具变成可嵌入的检索服务。
