为什么“硬件细节”决定训练成败?

显存不够

模型参数 + 梯度 + Adam 状态 + 激活 + buffer 超出 HBM, 只能切分或降精度。

通信太慢

万卡训练时, 一步里可能有多轮 AllReduce / ReduceScatter / AllGather。

存储太慢

预训练数据和 checkpoint 规模 TB-PB 级, I/O 抖动会让昂贵 GPU 等数据。

设施跟不上

单机柜几十到上百 kW, 风冷、供电、布线、消防、运维都成为约束。

LLM 训练的目标不是峰值 TFLOPS, 而是 持续数周保持高 MFU + 低故障恢复成本。

GPU 内部: 为什么 Tensor Core 重要?

普通 CUDA Core

适合通用标量/向量计算, 灵活但矩阵乘吞吐有限。

Tensor Core / Matrix Core

为矩阵乘累加设计, 支持 FP16/BF16/TF32/FP8/FP4 等低精度格式, 是 Transformer 训练主力。

Transformer 大头 ≈ GEMM: [tokens × hidden] · [hidden × 4hidden] 硬件目标: 让矩阵维度、batch、并行切分都“喂饱”Tensor Core。

训练性能常用 MFU(Model FLOPs Utilization) 衡量: 实际模型 FLOPs / 理论峰值 FLOPs。

HBM: 大模型训练的第一道墙

容量

能不能放下参数、梯度、优化器状态、激活。H200/MI300X 的大显存显著降低切分压力。

带宽

Attention、LayerNorm、optimizer update、通信 buffer copy 经常是 memory-bound。

位置

HBM 在加速器封装附近, 带宽远高于 DDR, 但容量昂贵且不可像普通内存随意扩展。

显存压力 ≈ 参数 + 梯度 + 优化器状态 + 激活 + 通信/临时 buffer

激活内存: batch、seq length 的隐藏杀手

为什么激活大?

反向传播需要中间结果: hidden states、attention scores、MLP 中间层。序列越长、micro-batch 越大, 激活越大。

硬件影响

长上下文训练往往不是参数先爆, 而是激活和 attention buffer 先爆 HBM。

activation checkpointing
→
重算 forward
→
省显存
→
多耗算力

硬件决策: 如果 HBM 贵且算力相对充裕, checkpointing 很划算; 如果通信/算力已满, 重算会拖慢 step time。

NVLink / NVSwitch: 节点内通信为什么快?

NVLink

GPU-to-GPU 高带宽低延迟互联。H100 代每 GPU 约 900GB/s, Blackwell 代约 1.8TB/s。

NVSwitch

把多颗 GPU 组成近似全互联域, 让任意 GPU 间通信不用绕 CPU/PCIe。

Tensor Parallel: 每层矩阵被切到多 GPU → forward/backward 中频繁 AllReduce / AllGather → 节点内 NVLink 带宽决定 TP 可扩展性

130TB/sNVLink domain bandwidth

GB200 NVL72 把 72 个 GPU 放进一个液冷 rack-scale NVLink domain, 目标是让 trillion-parameter 模型在更大的“近似单机”域中训练/推理。

趋势: 大模型硬件不再只卖“单卡”, 而是卖 rack-scale system + networking + software stack。

Collective 通信: 训练里最常见的网络动作

AllReduce

所有 GPU 的梯度求和再广播。数据并行最经典, 通信量随参数量增长。

ReduceScatter

先 reduce 再把结果切片分发。ZeRO/FSDP 常用, 减少每卡状态。

AllGather

每卡收集其他卡的 shard。FSDP forward 前常见。

All-to-All

MoE token dispatch 常见, 对网络抖动极敏感。

硬件含义: DP 更吃跨节点网络; TP 更吃节点内 NVLink; MoE 更吃 all-to-all 和负载均衡。

并行策略与硬件瓶颈映射

并行解决什么主要硬件压力适合场景
Data Parallel扩大 batch跨节点 AllReduce模型单卡/单节点能放下
Tensor Parallel切分层内矩阵节点内 NVLink大 hidden / 大 MLP / 注意力层
Pipeline Parallel按层切模型stage 间点对点通信模型深, 节点数多
ZeRO/FSDP切优化器/梯度/参数AllGather + ReduceScatter显存瓶颈明显
Sequence Parallel切长序列激活attention/activation 通信长上下文训练

Roofline 视角: 算力瓶颈 vs 带宽瓶颈

Compute-bound

大 GEMM, arithmetic intensity 高。目标是喂满 Tensor Core, 关注 tile、batch、kernel fusion。

Memory-bound

LayerNorm、softmax、optimizer、small op。目标是减少 HBM 读写, 关注 fusion、FlashAttention。

Arithmetic intensity = FLOPs / bytes moved

LLM 训练性能优化不是只“堆 FLOPS”, 还要让每次 HBM 读取产生更多计算。

FlashAttention 的硬件意义

传统 attention

显式生成 N×N attention matrix, 长序列时 HBM 读写和显存占用巨大。

FlashAttention

分块在 SRAM/register 里计算 softmax attention, 减少 HBM traffic, 让 attention 更接近 compute-bound。

CPU 和主内存: 不直接训练, 但会拖后腿

CPU 负责

  • 数据解码/tokenize
  • dataloader worker
  • 调度 runtime
  • 部分 checkpoint 压缩/校验

常见问题

  • CPU NUMA 绑错
  • host memory 不够
  • PCIe 拓扑绕路
  • 小文件数据集拖慢 I/O

高端 GPU 节点常见经验: CPU、DDR、NVMe、NIC 配置要为 GPU“供料”, 不是越省越好。

Checkpoint: 为什么训练不能只靠“保存模型”?

必须保存

  • 模型参数 shard
  • optimizer state
  • LR scheduler
  • RNG state
  • dataloader offset

硬件挑战

  • 写入时不能长时间阻塞 GPU
  • 数千进程同时写会打爆元数据服务
  • 恢复时要按拓扑重映射 shard

万卡训练的 checkpoint 设计是一套分布式存储系统, 不是一个 `torch.save()`。

700W+高端训练卡常见级别

风冷

部署成熟, 但高密度机柜越来越吃力。

液冷

GB200 NVL72 等 rack-scale 系统普遍走液冷路线, 需要机房设施配套。

网络拓扑: 不同拓扑决定扩展上限

Fat-tree / Clos

常见于 InfiniBand/RoCE 集群, 目标是高 bisection bandwidth。

Dragonfly / torus

用更少长链路连接分组, TPU Pod 等有专用拓扑。

Rail-optimized

多 NIC 多 rail, collective 库需要知道 GPU↔NIC 亲和性。

坏拓扑表现: 小规模 benchmark 很快, 一到 512/1024 GPU 后 step time 抖动、tail latency 放大。

GPUDirect RDMA: 为什么 GPU 能直接走网卡?

without GPUDirectGPU HBM→ CPU memory staging→ NIC
with GPUDirect RDMAGPU HBM→ NIC DMAless copy / lower latency

跨节点 collective 的关键是减少 host staging, 让 NIC 更直接地读写 GPU memory。

可靠性: 万卡训练必然遇到故障

硬件故障

  • GPU Xid / 掉卡
  • HBM ECC error
  • NIC link flap
  • SSD wear

系统故障

  • NCCL timeout
  • 进程 hang
  • 节点温度降频
  • 作业调度抢占

规模越大, MTBF 越短。训练平台要默认“每天都有节点坏”, 依靠 checkpoint + elastic restart。

Silent Data Corruption: 最难发现的硬件风险

显性错误

进程崩溃、ECC 报错、NCCL timeout, 虽然痛苦但容易定位。

静默错误

硬件/网络/内存返回错误结果但作业继续跑, 可能数天后才发现 loss 异常。

防护做法
硬件ECC, RAS, burn-in, 温度/电源监控
软件loss anomaly detector, checksum, gradient norm 监控
流程小规模 sanity run → 扩容 → 定期 eval checkpoint

Throughput

成本结构: CapEx / OpEx / Opportunity cost

CapEx

加速器、服务器、交换机、存储、机柜、液冷、机房改造。

OpEx

电费、冷却、带宽、运维、备件、云租赁、软件支持。

Opportunity cost

排队等待、低利用率、作业失败重跑、调试迁移带来的隐性成本。

便宜硬件如果导致软件适配慢、利用率低、重跑多, 总成本可能更高。

常见误区 1: TFLOPS 越高训练越快?

错误理解

只看单卡峰值 TFLOPS, 认为训练速度线性提升。

正确理解

实际速度 = kernel 效率 × HBM × 通信 × 数据供给 × 故障恢复。峰值只是上限。

如果 step time 里 35% 在通信, 单卡 FLOPS 翻倍最多也只能改善计算部分。

常见误区 2: 显存越大就不需要并行?

显存大能缓解

更大的 HBM 可以减少 ZeRO/TP 压力, 支持更长上下文和更大 batch。

但不能替代并行

训练时间要求决定必须用多卡; 多卡就必然涉及通信、调度、checkpoint 和故障恢复。

大显存让“能跑起来”更容易, 但“跑得快、跑得稳”仍靠系统工程。

常见误区 3: 网络买满带宽就行?

带宽只是一个维度

延迟、拥塞、拓扑、rail 绑定、collective 算法都会影响训练。

需要端到端验证

用 NCCL tests、真实模型 step time、故障注入一起测, 不要只看 iperf。

实验室/小团队怎么落地?

阶段 1: 单机 8 卡

先掌握 dataloader、混合精度、FSDP/DeepSpeed、监控和 checkpoint。

阶段 2: 2-8 节点

重点打通网络、NCCL、共享存储、Slurm/K8s 调度。

阶段 3: 64+ GPU

引入 topology-aware scheduling、异步 checkpoint、故障恢复演练。

阶段 4: 云/混合

对比云上 GPU/TPU/Trainium 的迁移成本和可获得性。

建议先把 7B/13B 小规模持续预训练跑稳定, 再扩展到更大模型。

未来趋势: AI 训练硬件会怎么变?

1. Rack-scale

NVL72/Pod 化, “一个机柜就是一个训练单元”。

2. 更低精度

FP8 成熟, FP4/混合量化进入训练/推理边界。

3. Memory-centric

HBM 容量、带宽、CXL/host memory、KV/activation 管理更重要。

4. Network-centric

all-to-all、MoE、长上下文让网络成为核心差异化。

5. Power-centric

每 MW token 产出成为 AI 工厂指标。

6. Software-hardware co-design

算子、编译器、并行策略与硬件拓扑一起设计。

总结: 大模型训练硬件的 6 条主线

  1. 算力: Tensor Core/Matrix Core 决定 GEMM 上限。
  2. 显存: HBM 容量/带宽决定能不能放下、能不能喂饱。
  3. 互联: NVLink/ICI 解决节点内, IB/RoCE/EFA 解决跨节点。
  4. 数据: 存储与 dataloader 决定 GPU 是否空转。
  5. 设施: 供电、散热、机柜密度决定能部署多大规模。
  6. 可靠性: checkpoint、监控、弹性恢复决定长跑是否成功。

一句话: LLM 训练是把 模型并行策略 映射到 硬件拓扑 的工程。
