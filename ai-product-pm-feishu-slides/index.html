🎯 核心场景

AI 项目 3 重风险: 算法不确定 / 跨角色协同 / 业务验收约束。
本套方案 = 应对这 3 重风险的全套打法。

项目背景 & 3 重风险

AI 算法研发 + 工程落地 + 业务验收 混合项目,3 重风险全程伴随

🔴 风险 1 · 算法不确定性

模板匹配 / 图像识别精度不可控,数据集标注迭代周期长,模型效果现场可能跟实验室不一致。

管理对策: 多轮迭代机制 + 现场环境提前纳入测试 + 持续模板更新流程

🟡 风险 2 · 跨角色协同

6 角色混合: 算法 / 标注 / 后端 / 前端 / 业务 / 测试,各角色关注点不同,沟通断层是延期主因。

管理对策: RACI 权责矩阵 + 飞书项目看板 + 跨角色同步会议

🟣 风险 3 · 业务验收约束

业务侧要求 识别准确率 / 漏检 / 误检 / 分拣效率 等硬指标,验收不通过要返工。

管理对策: 验收标准全部书面化 + 业务签字 + 现场逐项勾选

🟢 风险 4 · 持续迭代需求

上线 ≠ 结束,需持续补充 农产品模板 / 优化识别模型 / 适配新场景。

管理对策: 模板持续更新流程文档化 + 运维期任务模板化

核心洞察: AI 项目最大的 4 个风险,90% 出在"需求模糊 / 数据延迟 / 验收扯皮 / 上线后无人维护"——这 4 个都靠 文档化 + 流程化 + RACI 解决,而不是靠"加班"。

第 1 章 · 项目启动 ② 4 份核心基线文档

锁定范围,避免无限加需求——AI 项目最容易翻车在需求模糊

📄 文档 1 · 项目立项总文档 (总首页)

所有人第一看的文档,固定模块:

  • 项目目标:量化指标 (例:20 类农产品,误检率 < 1%,单图 < 200ms,分拣通过率 98%)
  • 干系人清单 + RACI 权责矩阵 (飞书 @ 人)
  • 整体总里程碑 (粗排 3-6 个大节点,录入飞书项目)
  • 预算、资源、硬件清单 (GPU / 相机 / 分拣设备)
  • 核心约束:交付时间 / 准确率底线 / 硬件成本上限
📄 文档 2 · 业务需求规格说明书 (业务侧唯一标准)

由 产品/业务 填写,飞书在线协同评审:

  • 农产品清单:需识别品类 + 特征模板 (大小/色泽/瑕疵/分级)
  • 分拣规则:合格/次品/分类逻辑
  • 识别场景:流水线动态拍摄 / 光照差异 / 遮挡 / 堆叠
  • 验收指标:准确率/漏检/误检/响应速度,全部书面化 + 业务签字

⚠️ 重点: AI 项目最容易翻车是需求模糊,所有验收标准必须书面签字。

📄 文档 3 · 项目组织与协作规范 (统一工作方式)

飞书文档固化协作规则:

  • 会议机制:晨会 / 周会 / 算法评审会 / 业务同步会 (固定飞书日程)
  • 文档规范:统一命名规则 / 存放路径 / 更新人
  • 反馈渠道:bug / 算法问题统一飞书项目提任务,禁止私发
  • 权限分级:标注员仅看数据集 / 算法可读全部技术 / 业务仅可读需求验收
📄 文档 4 · 风险初始清单 (启动阶段就识别 AI 特有风险)

示例 AI 项目风险 (启动时就要建好):

  • 数据集不足 — 农产品数据采集难,品类不全
  • 模板相似度高 — 部分农产品外观相近,易混淆
  • 现场光照干扰 — 实验室 OK 现场崩
  • 硬件延迟 — 推理服务响应不达 200ms
  • 业务临时新增品类 — 范围蔓延

每条标注:影响等级 / 应对预案 / 负责人

4 份基线文档的总原则: 范围不清不写代码 · 验收不明不写代码 · 权责不明不写代码 · 风险不明不写代码。

第 2 章 · 规划阶段 ① WBS 5 大层拆解

AI 识别项目专属拆解,5 大层 × 4-5 子项 = 23 个原子任务

1. 业务与数据层 1.1 农产品图像采集 1.2 数据标注规范制定 1.3 数据集标注、清洗、增广 1.4 数据集版本管理 2. AI 算法模板识别层 2.1 模板匹配算法选型 (传统模板 / YOLO / 特征匹配) 2.2 基线模型训练 2.3 多版本模型对比测试 2.4 瑕疵 / 分级模板优化迭代 3. 系统工程层 3.1 图像采集对接相机 SDK 3.2 AI 推理服务封装 3.3 分拣联动后端接口 3.4 可视化后台 4. 测试验收层 4.1 算法指标测试 4.2 整机流水线联调测试 4.3 现场小批量试生产测试 5. 交付运维层 5.1 部署包制作 5.2 现场落地调试 5.3 模板持续更新机制搭建

WBS 拆解的 3 个原则

原则 1 · 每条任务 ≤ 2 人天

超过 2 人天的子项要再拆;估时不准时,把"完成"具体化。

原则 2 · 显式依赖关系

每条任务标"前置依赖"。例:2.2 依赖 1.3 完成;3.1 依赖 3.2 接口定义。

原则 3 · 交付物必须明确

每条任务必有"交付物"——飞书文档链接 / 代码 commit / 报告。

飞书落地: 23 个原子任务全部录入飞书项目,按 5 大阶段分泳道,任务附件挂对应飞书文档链接。
重要: 数据标注任务单独建一个飞书多维表格跟踪每日产能(见 slide 16)。

第 2 章 · 规划阶段 ④ 变更管理机制

AI 项目重中之重——不加变更流程 = 无休止改模板 / 加品类

AI 项目变更灾难典型: "再加 3 个品类就行" → "模板再调一下" → "识别规则改一下" → 项目延期 2 倍。

📋 飞书《需求变更申请单》固定流程

① 申请人填写

变更内容 / 影响范围 (数据集 / 模型 / 工期 / 成本) / 紧急程度

② 三方评审 (飞书评论审批)

算法 + 业务 + 项目负责人 三方评论确认,任何一方反对 = 不通过

③ 通过后同步更新

需求文档 / 排期表 / 飞书项目任务 三处同步更新,不留版本不一致

④ 未走流程 → 一律不执行

无论谁口头说"加这个吧",没走变更单就不动。

变更分级 (按影响范围)

等级影响处理
L1 小变更 单任务 < 2 天 / 0 成本 PM 直接审批
L2 中变更 1 周 / < 1 万 / 1-3 任务 算法+业务+PM 三方评审
L3 大变更 > 1 周 / > 1 万 / 影响里程碑 + 技术总监 / 业务总监
L4 颠覆 目标重定义 / 范围重谈 启动新项目
变更台账: 飞书多维表格《变更登记》,字段:编号/申请人/等级/影响/审批人/状态/完成时间
目的: 任何变更都可追溯,周会复盘"本月改了几次",识别"业务需求飘移"信号

问题卡点的根因是什么?穿透到机制层。

🚀 模块 4 · 后续 AI 项目改进方案

针对根因,下一个项目要改什么?具体到模板 / 流程 / 文档

例: 立项时加 1 名业务方标注审核员 + 标注规范双签

复盘的"3 不"原则

🚫 不批斗个人

对事不对人,讨论"机制哪里缺",不讨论"谁犯了错"

🚫 不只夸不批

只夸 → 没有改进价值;只批 → 团队不敢说真话

🚫 不悬而未决

每个"问题卡点"必须出 1 条"改进方案",有 Owner + 截止时间

第 6 章 · AI 项目专属避坑 + 9 步落地

针对模板识别项目 4 条避坑 + 你可以立刻照做的 9 步落地

🚫 4 条 AI 项目专属避坑

坑 1 · 数据标注 = 第一生命线 (单独里程碑)

很多 AI 项目延期都是 标注滞后。单独建飞书表格跟踪每日标注产能,提前储备标注人力,清晰标注规范减少返工。

坑 2 · 模板识别 = 迭代特性 (预留 2-3 轮优化)

不要只规划一轮训练。排期预留 2-3 轮模板优化任务,每轮效果全部记录在实验文档,量化迭代提升幅度。

坑 3 · 业务现场环境提前纳入测试

光照 / 遮挡 / 流水线速度 / 真实拍摄角度,提前写入测试用例。避免"实验室 98% → 现场 70%"的崩盘。

坑 4 · 模板持续更新流程 (上线 ≠ 结束)

文档固化 新增模板采集 / 标注 / 重训 / 更新推理服务 的标准化流程,方便后期运维迭代。

✅ 9 步落地执行 (你可以立刻照做)

📋 启动日 → 上线日 全流程
① 飞书创建多维空间 + 项目群 + 飞书项目看板 ② 复制 7 套标准管理文档模板, 填充本项目基础信息 ③ 输出立项文档 + 需求说明书, 组织业务 & 技术评审签字 ④ 拆解 WBS (5 大层), 制作排期多维表格 批量创建飞书项目任务并绑定文档 ⑤ 启动数据采集标注任务, 同步维护数据集 + 模板库文档 ⑥ 按日 / 周固定会议, 持续更新周报 + 风险台账 + 算法实验记录 ⑦ 阶段性算法评审 (每 2 周), 不达指标立即新增优化任务 ⑧ 完成联调 + 现场验收, 整理全套交付文档 ⑨ 编写复盘文档, 统一归档所有资料
9 步对应 5 大阶段: ①② 启动 / ③④ 规划 / ⑤⑥⑦ 执行 / ⑧ 监控 + 收尾 / ⑨ 复盘归档
关键: 9 步不是 串行,而是 部分并行:③ 评审签字跟 ④ 拆解 WBS 可以并行;⑥ ⑦ 持续运行 6-12 周。

  • Q: 飞书 vs 钉钉 vs 企业微信? A: 飞书在 多维表格 + 文档协同 + 项目联动 上最强,AI 项目 PM 首选。
