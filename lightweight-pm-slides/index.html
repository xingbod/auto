"进度说不清"在小团队里的 5 大典型症状

症状 1 · 老板问进度

老板/干系人问"什么时候能上线",你答不上来,只能说"快好了" / "再一周" / "差不多了"。
本质: 没有可视化的进度,只有"感觉"。

症状 2 · 团队成员不知道整体进度

小 A 在做"用户登录",但不知道登录做完之后是接支付还是接权限,做完才发现下游要返工。
本质: 任务依赖没有写明,信息分散在每个人脑子里。

症状 3 · 多任务并行混乱

3 个人同时在做 5 件事,每件事都"做了一半",没有一件是"完成"的。
本质: WIP(在制品)没限制,上下文切换成本爆炸。

症状 4 · 估时永远不准

说好的"3 天做完",结果拖了 2 周;或者提前 1 周做完,但"做完了"≠"能上线"。
本质: 任务没拆到"可验证"粒度,完成定义模糊。

症状 5 · 状态汇报靠"问"

想了解项目状态,只能挨个私聊问;问出来还不一定是真的(大家倾向于"报喜不报忧")。
本质: 没有"透明可视化"机制,只能口头同步。

✅ 解决思路

5 大症状归结起来是 1 件事:进度不在文档里,只在人脑里。
解法 = 把进度从人脑搬到文档,用"文档 + 人"替代"工具 + 仪式"。

关键洞察: 这 5 个症状的根因是同一个——进度不在文档里,只在人脑里。下面整套方法就是把这个"根因"彻底解掉。

核心思路:文档 + 人,不靠工具 + 仪式

Basecamp Shape Up / Amazon Working Backwards 的现代轻量版

📚 文档 = source of truth

PRD / TDD / Task List / ADR 四类核心文档,加上周报 / changelog / 决策记录,把所有"重要信息"留在纸面上。

新人加入项目 = 读 4 篇文档,而不是问 10 个人。

👥 人 = 协调者

PM 盯 优先级 / 风险 / 干系人沟通。
Dev 盯 任务执行 / 代码质量。
每周一次同步会,其他时间异步。

不是"工具自动协调",是人 review 文档 + 异步沟通。

🚫 不做什么

❌ Scrum Master 角色
❌ Sprint Planning 2h
❌ Story Point + Burndown
❌ Jira 完整 workflow
❌ 每日 15min standup 仪式

3-8 人做这些是"为流程而流程",80% 是负担。

公式: 轻量 PM = 3 大文档 + 3 套同步机制 + 4 个度量数字 + 1 个 PM 盯全局。
为什么不用 Agile? Agile 解决的是 "需求频繁变化 + 团队规模大 + 跨地域协调"。3-8 人小团队 + 需求相对稳定 + 都在一个办公室,这些痛点根本不存在。

第 1 章 · 方法论选择

为什么小团队不上 Agile / Scrum / Kanban 也能管好

常见痛点Agile 解法小团队真相轻量解法
需求变化快 短 Sprint + 频繁 review 3-5 人靠午饭就能聊清楚 PRD 每月更新 1 次,需求变更走文档
团队规模大 拆分 Squad / Tribe 3-8 人根本不用拆 不拆,所有人能看到所有任务
跨地域协调 Daily standup + Slack 都在一个办公室 现场对话 + 异步文档
进度不透明 Burndown chart 8 人以下数据点太少,曲线无意义 任务清单 + 周报
代码质量 Definition of Done + CI 本来就 1-2 个 reviewer PR review + checklist
沟通成本 Scrum Master 协调 PM 直接盯,无需中间层 PM 一肩挑(协调 + 优先级 + 干系人)
结论: Agile 的 6 大痛点中,小团队 天然解决了 5 个(规模、跨地域、沟通、进度、代码),只剩下"需求变化"一个,但 1 个月更新一次 PRD 就够了。

3-8 人小团队的 3 个推荐工作流

⭐ 轻量 Scrum (本课重点)

1 周一个 mini-cycle,周一更新 PRD,周中 30 分钟对齐,周五更新进度。
适合: 需求相对稳定、有明确里程碑的项目。

Shape Up (Ryan Singer / Basecamp)

6 周一个 cycle,前 2 周 shaping,后 4 周 building,无 sprint ceremony。
适合: 需求变化快、想避免"伪敏捷"的小团队。

Kanban 滑动

无固定 cycle,WIP 限制 + 持续流动。
适合: 维护型 / 运维型 / 多模块并行项目。

本课聚焦 ⭐ = 轻量 Scrum。其他两种思路类似,只是 cycle 长度不同。

PRD 5 大模块模板

一页纸讲清楚"做什么 + 为什么 + 算做完"

1
背景 & 目标 (Why)

解决什么问题?目标用户是谁?上线后怎么衡量成功?
例: 注册转化率从 18% 提升到 25%

2
用户场景 (Who & When)

3-5 个核心场景,每个场景一段话 + 关键触点。
例: 新用户首次访问 → 注册 → 邮箱验证 → 进入 dashboard

3
功能清单 (What)

用列表列功能,每条加 优先级 (P0/P1/P2) 和 验收标准。
P0: 必须做 / P1: 强烈建议 / P2: 时间允许

4
非功能需求 (Quality)

性能 / 安全 / 兼容性 / 数据合规。
例: 页面加载 < 2s;支持 Chrome 100+;用户数据加密存储

5
不在范围内 (Out of Scope)

明确"这次不做"的,避免范围蔓延。
例: 多语言支持 / 第三方登录 / 移动端 App

📝 PRD 真实示例 (节选)
# PRD-007 · 邀请返利系统

## 1. 背景
老用户拉新转化率低 (< 5%),希望通过
老带新奖励激活社交传播。

## 2. 目标
3 个月内老带新比例达 15%。

## 3. 用户场景
- 老用户 A 分享链接 → B 注册 → A 获 10 元券
- B 下首单 → A 再获 20 元券

## 4. 功能清单
- P0: 分享链接生成 + 二维码
- P0: 邀请关系绑定
- P0: 券发放 + 状态追踪
- P1: 邀请排行榜
- P2: 邀请海报模板

## 5. 不在范围
- 多级分销 / 团队奖励 / 海外用户
模板原则: 1 个 PRD = 1 个独立功能/项目。更新时记录 diff(谁改了什么),不要 overwrite 历史。

TDD 技术设计文档怎么写

回答"怎么做"+"为什么这么做",给未来回看留路标

TDD = 4 大模块

① 架构图 (ASCII / Mermaid)

系统模块 + 数据流 + 关键依赖。
不是"画得漂亮",是"能讲清楚边界"

② 关键决策 (Trade-off)

选了什么?放弃了什么?为什么?
例: 选 PostgreSQL 而非 MongoDB,因为需要事务 + 强 schema

③ 接口契约 (API Contract)

核心接口的入参 / 出参 / 错误码。
不要全列,只列"关键 + 易变"那 20%

④ 风险 & 回滚方案

已知风险 / 缓解措施 / 如果上线挂了怎么回滚。
回滚方案 = 必填,不是"上线再说"

进度专题 ① 拆任务到能说清进度

为什么"做了一半"这种话说不清?因为任务粒度太粗

❌ 拆得不好的任务

典型坏例子

「做邀请返利系统」

估时: 2 周
进度: 60%
问题: 60% 是什么意思?哪些部分 OK 哪些挂了?谁都不知道。

症状: PM 问"做到哪了",回答永远是"快了""差不多了""再两天"——但"两天"永远不会到。

✅ 拆得好的任务

3 层拆解 + 2 元状态
📦 L1 大任务: 邀请返利系统 (2 周)
  ├── L2 中任务: 链接生成 + UI (1.5d)  ✅ DONE
  ├── L2 中任务: 关系绑定 (1d)        🔵 DOING
  ├── L2 中任务: 首单发券 (2d)         ⚪ TODO
  ├── L2 中任务: 后台看板 (2d)         ⚪ TODO
  ├── L2 中任务: 客服 FAQ (0.5d)       ⚪ TODO
  └── L2 中任务: 性能压测 (1d)         ⚪ TODO

进度: 1/6 完成 = 17% (可量化)
     + 1/6 进行中 (L2 + L3 都有具体子任务)
预计上线: 还需 5 个工作日

3 条拆解规则

  • 规则 1 · 2 元状态: 每条任务都能回答"做完/没做完",禁用"做了一半" / "基本完成"。
  • 规则 2 · ≤ 2 人天: 估时不超过 2 个工作日。超过就再拆,直到 ≤ 2 人天。
  • 规则 3 · 显式依赖: 每条任务标"依赖"——前置任务没完,这条不动。避免多个人同时改一个东西。
核心收益: 拆完后,PM 一眼能答 "完成 1/6,进行 1/6,阻塞 0,预计 5 天"——不再靠"感觉"。

进度专题 ② 3 套同步机制

替代 Scrum 的 4 个仪式(daily/plan/review/retro),保留沟通 + 砍掉仪式

① 周一 · 30 分钟对齐会

议程固定 3 项:

  • 上周做了什么 (3 分钟)
  • 本周要做什么 (10 分钟)
  • 有什么阻塞 + 谁来解决 (15 分钟)

替代: Sprint Planning + Review
频率: 每周一次,30 分钟硬上限

② 异步 · 文档 review

3 类文档异步 review:

  • PRD 更新 → 评论 / 标注
  • TDD 改动 → Slack 通知 + 评论
  • Task 状态 → 任务清单直接改

替代: Daily standup
频率: 文档一改就 @ 相关人,24h 内 review

③ 现场 · 走到桌边

3 类问题立刻聊:

  • 阻塞超过 2 小时
  • 决策需要 2+ 人同意
  • 任务依赖关系不清楚

替代: Retrospective + 临时会议
频率: 触发即用,5-15 分钟

3 套机制总时长: 30 分钟/周 + 异步 + 现场 5-15 分钟/次 = 3-8 人小团队一周总沟通时间 ≈ 2-3 小时。比 Scrum 仪式 (4-6 小时/周) 节省 50%+。

周一对齐会 5 段议程模板 (30 分钟硬上限)

00:00-00:03 上周完成 (每人 1-2 句) 00:03-00:15 本周计划 (PM 念,大家补充) 00:15-00:27 阻塞讨论 (按优先级排,大阻塞先聊) 00:27-00:29 风险预警 (新出现的风险/依赖) 00:29-00:30 下次周会时间 + 收尾

进度专题 ③ 3 数字汇报法

老板/干系人问"什么时候能上线"?——用 3 个数字回答

❌ 常见的 3 种"答非所问"

答法 1 · "快了"

老板问什么时候上线,你说"快了"——信息量为 0。老板只会被反复问"到底什么时候"消耗信任。

答法 2 · "再 1 周"

每次都说"再 1 周",3 周后还没上线——把单次延期变成系统性失信。老板不再相信你说的任何时间。

答法 3 · "90% 了"

"做了 90% 了,卡在最后一个 bug"——90% 是感觉,不是数据。bug 可能 1 天修完,也可能要重写核心模块。

✅ 用 3 个数字说清进度

汇报模板 (60 秒说清)
"返利系统进度:
1. 完成率 60% (9/15 任务 done)
2. 剩余 5 个工作日 (基于历史速度估算)
3. 1 个高风险阻塞 (券服务 QPS 上限,
   需要先压测+扩容,小李在跟)

最坏情况: 如果阻塞没解决,
可能延期到 X 月 X 日,届时是否接受?"
公式: 完成率 (X%) + 剩余时间 (N 天) + 风险 (M 个) = 60 秒可汇报, 老板 30 秒可决策。
进阶: 每月给干系人发一份 1 页进度简报,3 数字 + 1 张图(任务燃尽)+ 1 段文字(本月高亮 + 下月计划)。

数字 1 拆解:完成率怎么算才不撒谎?

方法公式优缺点
任务数比例 完成数 / 总数 (例: 9/15 = 60%) ✅ 简单直观   ❌ 不考虑任务大小
工时比例 已完成工时 / 总工时 ✅ 反映真实工作量   ❌ 需要估时准确
里程碑比例 达成里程碑数 / 总里程碑数 ✅ 反映关键节点   ❌ 不反映任务细节
推荐: 任务数 + 里程碑双指标 任务 9/15 + 里程碑 1/3 ✅ 既有细节又有节点,最不容易撒谎

第 4 章 · 流程机制 · 代码 Review

小团队代码 review 的 3 个核心问题:谁 review / 怎么 review / 多快合并

3 种 review 模式对比

① 配对 review (Pair)

2 人一起写 + 一起看,实时反馈。
适合: 核心模块 / 复杂 bug / 新人 onboarding
缺点: 占用 2 人时间,小团队慎用

② 异步 review (Async PR) ⭐ 推荐

开发提 PR → 1-2 个 reviewer 异步看 → 评论 / 改 → 合并。
适合: 日常功能开发 / 重构
SLA: 24h 内首次 review,小改动 4h 内

③ 准入 review (Gate)

只在合并到 main / 上线前 review。
适合: 关键路径 / 安全相关 / 性能敏感
缺点: 反馈太晚,改起来成本高

PR Review Checklist (10 项)

📋 Reviewer 看什么
  • ☐ 命名规范 + 代码风格一致
  • ☐ 函数/类 单一职责,不超 200 行
  • ☐ 没有 魔法数字,常量都有名字
  • ☐ 错误处理完整,不吞异常
  • ☐ 日志规范,关键操作有 log
  • ☐ 单元测试覆盖核心逻辑 (≥ 70%)
  • ☐ 没有 PII / 密钥硬编码
  • ☐ DB migration 兼容旧版本
  • ☐ 性能影响评估 (大查询 / 慢接口)
  • ☐ 文档同步更新 (PRD/TDD/API doc)
准入准出标准 (Definition of Done): PR + ≥ 1 reviewer 通过 + CI 全绿 + 测试覆盖 + 文档更新 = 才能合并到 main。
🚫 不要: 自我合并 + 紧急跳过 review + "先合并后改"。一旦开了口子,代码质量立刻雪崩。

发布管理 · 语义化版本 + Changelog

用户和客服能感知"这个版本改了什么",出问题时能快速定位

语义化版本 (SemVer) 三段式

v1.4.2 怎么读
v MAJOR . MINOR . PATCH
  ↑         ↑         ↑
  │         │         └── 修复 bug,小调整
  │         └──────────── 新功能,但向后兼容
  └────────────────────── 破坏性变更

例:
v1.0.0  → 上线初始版本
v1.1.0  → 加了邀请返利功能
v1.1.3  → 修 3 个 bug
v2.0.0  → 重构返利系统,API 不兼容
怎么定版本号: PM + Tech Lead 在每次 release 前 5 分钟定,不靠"我随便填一个"。

  • 上线翻车了 → 第一件事:加一条 Checklist
  • Checklist 不要超过 10 条,多了没人用
🚫 常见反面例子

  • "监控不用配,新接口很简单" → 接口报错没告警,半夜被打爆

决策记录 ADR · 重大决策留痕

"为什么当初选 A 不选 B"——3 个月后没人记得,文档替你记得

什么时候要写 ADR?

✅ 必写 ADR 的 5 类决策
  • 技术选型 (数据库 / 框架 / 云厂商)
  • 架构调整 (单体→微服务 / 同步→异步)
  • 引入新依赖 (新 SDK / 新服务)
  • 数据相关 (schema 大改 / 删除数据)
  • 跨团队协议 (API 规范 / 事件格式)
什么时候不写: 1 天内能改回去的决策 / 个人偏好 / 内部小重构。ADR 不是事无巨细的日志。

ADR 模板 (Michael Nygard)

📋 ADR-007 · 邀请返利数据存储选型
状态: 已接受 (2026-06-15)

背景 (Context):
返利系统需要记录邀请关系 + 券发放状态,
数据量大(预计 100 万行/月),有事务需求。

决策 (Decision):
选用 PostgreSQL,在 users 表加 invite_by
字段,invitations 表单独存关系链。

后果 (Consequences):
+ 事务保证,不用补偿
+ 强 schema,字段变化可控
- 写性能不如专用 KV
  (QPS < 5000 时无影响)

替代方案 (Considered):
❌ MongoDB: 事务支持弱
❌ Redis: 持久化成本高
❌ ClickHouse: 不适合单行查询
ADR 的最大价值: 未来有人说"为什么不用 MongoDB",你不需要回忆或现场讨论——看 ADR-007 就知道。新人 onboarding 也靠这套。
存放位置: docs/adr/0001-xxx.md 0002-yyy.md 顺序编号,Git 跟踪。永远不删,只标 "Superseded"。

变更控制流程

📝 任何变更走 3 步

① 写变更单:什么 / 为什么 / 影响范围 / 回滚方案
② 评审:PM + Tech Lead + 相关方 (5-15 分钟)

4 个数字怎么算 + 怎么用

数字怎么算健康区间异常时怎么办
Sprint 完成率 本周完成 / 本周计划 70% - 90% < 60%: 计划太多 / > 95%: 计划保守 (团队没挑战)
Cycle Time 任务从 DOING 到 DONE 的天数 ≤ 5 天 (95 分位) 过高: 任务太大 / 卡在 review / 等待依赖
返工率 返工任务数 / 总完成任务数 ≤ 10% 过高: 需求不清 / 测试覆盖不足 / design review 缺
关键 Bug 数 本周发现 Severity 1 bug 数 ≤ 3 个 过多: 测试薄弱 / 上线太快 / 没灰度
数据来源: 任务清单 (Task List) + Bug 跟踪 (GitHub Issues / Linear) + Release 记录。全部从已有工具取数,不引入新的指标系统。
展示方式: 月度复盘时画 4 条折线 (1 月-12 月),看趋势比单点数字更有意义。

月度复盘 · 4 个问题 + 1 个改进项

每月最后一周五下午,1 小时 4 问 1 改

4 个必答问题

① 我们这个月达成了什么?

列 3-5 个具体成果 (上线了什么 / 解决什么问题 / 关键指标变化)。
不是"我们很努力",是"我们做了什么"

② 什么没达成?为什么?

诚实列出 1-3 个没达成的目标 + 根因。
重点找"系统性问题"而非"个人失误"

③ 哪 1 件事最值得改进?

从问题清单中选 1 个最影响产出的。
只选 1 个,贪多嚼不烂

④ 下个月怎么做?

针对选出的 1 件事,定具体的 行动 + 负责人 + 截止日。
下次复盘第一项:上次行动有没有做到

月度复盘会议模板 (60 分钟)

📋 议程
00:00-00:10 本月数据 (4 个数字 + 趋势) 00:10-00:25 问题 1: 达成了什么 (自由发言) 00:25-00:40 问题 2: 什么没达成 (按优先级) 00:40-00:50 问题 3: 投票选"最值得改进的 1 件事" 00:50-00:55 问题 4: 定行动 + Owner + 截止日 00:55-01:00 写入文档 + 下次复盘时间确认
复盘文档: 用 1 个 Notion 页面,每月追加 1 个 section。1 年后回头看,能看到团队的成长曲线。
🚫 不要: 月度复盘变成批斗会 / 变成"赞美大会" / 改进项没人跟进。

为什么是这 4 个?

✅ 选它们的理由
  • Notion: 文档 + 数据库 + 模板,3-8 人免费够用
  • GitHub: 代码 + PR + CI + Release 一体化
  • Linear: 极简任务管理,3-8 人免费,比 Jira 快 10 倍
  • Slack/飞书: 异步沟通 + 集成 GitHub/Linear 通知
  • 互相集成: Notion ↔ GitHub ↔ Linear 双向链接
❌ 不要选的 (对小团队是负担)
  • Jira: 30+ 字段、50+ workflow 状态、2 个 PM 都配不完
  • Asana / Monday: 功能强但对小团队过度设计
  • 企业微信 + 钉钉 + 飞书 + Slack 混用: 信息 4 处分发,没人看得过来
  • 自建 dashboard: 3-8 人没有维护资源
  • 每日 15min 视频会议: 替代异步沟通后变成"为开会而开会"
工具选型原则: 每个工具都问"它解决的具体痛点是什么?不用会怎样?"——答不上来就别上。

5 大常见坑

小团队"文档驱动 + 人工控制"最容易踩的 5 个雷

坑 1 · 文档写完就过期

症状: PRD 写完后没人更新,3 个月后跟代码完全对不上。
解法: 每次代码改动问"PRD/TDD 要改吗",作为 PR 模板的必填项。

坑 2 · 假同步 (Pseudo Sync)

症状: 周会开完大家以为自己对齐了,实际各做各的。
解法: 周会最后 5 分钟,每人 1 句话重复"我下周要做什么"。

坑 3 · 范围蔓延 (Scope Creep)

症状: "再加个小功能就行" → 3 周后 MVP 还没上线。
解法: PRD 必填"不在范围"section,任何范围外改动走 RFC。

坑 4 · 英雄主义 (Hero Syndrome)

症状: 关键活全在一个人脑子里,TA 一请假/离职项目就停。
解法: 强制要求关键决策 / 设计都写文档,而不是"TA 知道"。

坑 5 · 决策无记录

症状: 3 个月后回头问"当初为什么这么选",没人记得。
解法: 重大决策走 ADR,所有 trade-off 文档化。

🎯 共同根因

5 个坑的根因都是 "信息没落在文档里,只在人脑里"。
每次想"算了这次口头说一下"——大概率就是 5 个坑的种子。

Q&A + 参考资源

一页带走 + 推荐书 / 文档 / 工具

✅ 本课核心要点

  • 核心思路: 文档 = source of truth,人 = 协调者,不上 Agile 也管好
  • 3 大文档: PRD (做什么) + TDD (怎么做) + Task List (谁来做)
  • 3 套机制: 周一 30min 对齐 + 异步文档 review + 现场对话
  • 3 数字汇报: 完成率 + 剩余时间 + 风险数
  • 4 度量: 完成率 / Cycle Time / 返工率 / 关键 Bug 数
  • 1 个 PM: 盯优先级 + 风险 + 干系人沟通
进度说不清的解法 = 任务拆细 + 状态文档化 + 3 数字汇报 + 周一对齐会。

❓ 常见追问

  • Q: 完全没有流程不行吗? A: 3-8 人 OK,但要文档化 + 周一同步,缺一不可。
  • Q: PM 一个人能盯这么多事吗? A: 文档化后,PM 只看 1 页 task list + 1 页风险表,5 分钟/天。
  • Q: 团队扩大后呢? A: 8 人以下用本课方法;8-15 人加 1 个 Tech Lead;15+ 人用 SAFe。
