"Token 压缩" = 在几乎不损失精度的前提下,把模型内部或输入/输出的 token 数量减少 4-16×。包括:减少 输入 token、KV cache、视觉 token、输出 token。

5 大技术路线 · 一图看清边界

Token 压缩不是单一技术,是一组针对不同对象的优化方法。

① Visual Token (ViT 时代)

图像 patch token 减少

  • 对象:ViT 内部 patch 序列
  • 代表:ToMe / DynamicViT / DiffRate
  • 目标:减少 vision 计算量
  • 典型压缩率:40-70% token 减少

② KV Cache (LLM 长上下文)

推理时 attention KV 压缩

  • 对象:推理时每 token 的 K/V 矩阵
  • 代表:H2O / StreamingLLM / KIVI
  • 目标:支持 1M+ token 上下文
  • 典型压缩率:5-100× KV 减少

③ Prompt / Context (LLM 输入侧)

压缩输入提示词

  • 对象:用户/系统输入的 prompt
  • 代表:LLMLingua / Selective Context / ICAE
  • 目标:降本(API token 计费)+ 提速
  • 典型压缩率:5-20× 字符减少

④ 长上下文 (位置编码 + 检索)

扩大 context window

  • 对象:RoPE / ALiBi 等位置编码
  • 代表:YaRN / LongRoPE / Landmark
  • 目标:从 8K 扩到 1M+ token
  • 典型扩展:100× context 长度

⑤ 投机解码 (输出侧)

多 token 并行生成

  • 对象:输出 token 序列
  • 代表:Medusa / EAGLE / SpecDec
  • 目标:加速 2-3× 推理
  • 典型加速:2-3× 速度

⑥ (横向) 评测 (贯穿 5 类)

如何衡量"压缩后还好不好"

  • 对象:压缩前后的能力保留度
  • 代表:RULER / LongBench / Lost in Middle
  • 目标:可量化的"无感压缩"
  • 关键指标:PPL / Accuracy / 速度 / 显存

① Visual Token 压缩 · 基础

ViT 把图像切成 16×16 = 256 patch(ImageNet),196 个(ViT-B/16),大量 patch 互相冗余。

1234 5637 891011 12131415 16171218

·保留 token  ·剪枝掉(drop)  ·合并到其他 token(merge)

两类核心方法

prune vs merge

  • Pruning(剪枝):直接丢弃冗余 token
  • Merging(合并):把相似 token 融合成 1 个
  • 合并 信息损失小,剪枝 速度快

核心问题

怎么判断哪个 token 不重要?

  • 基于 attention 分数(DynamicViT)
  • 基于 token 相似度(ToMe)
  • 基于 分类置信度(A-ViT)
  • 基于 可微搜索(DiffRate)

评价指标

  • FLOPs:计算量减少
  • Throughput:吞吐加速
  • Top-1 准确率:精度损失
  • Token 保留率:50-70% 常见

代表作 · ToMe(2023)· ~700 引

Token Merging: Your ViT but Faster · Bolya, Fu, Dai, Zhao, Feichtenhofer(Google)

核心思想

  • 对 ViT 无需训练,直接 token 合并
  • 每两层 block 之间插一次 token merge
  • 用 相似度 + 二分匹配 决定哪些 token 合并

关键算法

1. 计算 token pair 余弦相似度
2. 构造相似度图
3. 二分匹配(bipartite soft matching)
4. 选 r/2 对 token 平均合并

效果

  • ImageNet ViT-L 2× 加速 + 0.3% 掉点
  • ViT-H 1.8× 加速
  • 对 MAE / DINO 也有效
  • 无需训练,5 行代码集成
启示:"无需训练 + token 合并" 打开了"后处理优化"的新范式。ToMe 的二分匹配思想被多个后续工作(STA、Token Merging MoE)继承。

代表作 · DynamicViT(2021)· ~700 引 · ICCV 2023

Adaptive Token Pruning for Efficient Vision Transformers · Rao et al. (微软)

核心思想

  • 用 轻量 MLP 预测 token 重要性
  • 逐层 动态剪枝:从浅到深逐步减少
  • 训练一次,推理时 自适应 选 token

模块设计

  • Prediction Module:1 层 MLP,输出 token 保留概率
  • Pruning Module:Top-K 选重要 token
  • Masked attention:剪枝后做 soft attention

效果

  • DeiT-S 1.5× 加速 保持精度
  • ViT-B 1.3× 加速
  • 不同输入图像剪枝数量 自适应
启示:"输入自适应"剪枝 比统一剪枝更高效。简单图像剪得多,复杂图像保留多,这是动态计算的核心思想。

A-ViT(2022)+ DiffRate(2023)+ 后续

Visual token 压缩的两个新范式:自适应停止 + 可微搜索

A-ViT(Yin et al. AAAI 2022)· ~200 引

Tokens-to-Token ViT with Adaptive Computation

  • 每个 block 配 adaptive head,决定该 block 是否"提前退出"
  • 简单图像:第 5 层就退出(只跑 1/3 计算量)
  • 复杂图像:跑完全部 12 层
  • 训练时加 Gumbel-softmax 触发早退

DiffRate(Tang et al. NeurIPS 2023)· ~150 引

Differentiable Compression Rate

  • 把每层 token 保留率做成 可微参数
  • 用 Gumbel-softmax 端到端优化
  • 结果:ViT 自动决定"每层保留多少 token"
  • 比 DynamicViT 更灵活,精度更高

视频 Token 压缩 · 时空联合

视频 = 图像 token × 时序。ViViT / TimeSformer 等单帧方法扩展为时空方法。

核心挑战

  • 单帧图像 196 token,视频 16 帧 = 3136 token
  • 时空双维度冗余
  • 运动信息难丢弃
  • 推理实时性要求高

代表方法

  • VideoGPT · VQ-VAE 压缩时空
  • TokenLearner(2022) · Google · ~500 引
  • ST-Adapter · 时空 token 适配
  • VideoMAE(2022) · 掩码自编码
  • TubeViT / MaskViT · 视频 token 剪枝

2024 进展

  • Video Token Merging(ToMe 视频版)
  • Motion-aware pruning(运动感知剪枝)
  • Video LLM 上下文长 × 时序长
  • VideoLLaMA / VideoChat 量化
关键 insight:运动 token 重要,静态 token 冗余。按光流 / motion score 优先保留动态区域 token,这是视频 token 压缩的核心。

② KV Cache 压缩 · 为什么是 LLM 的头号瓶颈

LLM 推理时,每生成 1 个 token 都要把之前所有 token 的 K/V 矩阵存下来,显存随 sequence length 线性增长。

KV Cache 是什么

memory layout

  • 每个 transformer 层有 K 和 V 两个矩阵
  • 每 token 占 2 × num_layers × num_heads × head_dim × dtype
  • FP16 → 7B 模型的 100K context = 14GB

5 类压缩思路

  • ① 稀疏 attention:跳过不重要位置
  • ② 滑动窗口:保留最近 N 个
  • ③ 重要 token:heavy hitter 优先
  • ④ 低比特量化:KIVI / KVQuant
  • ⑤ 跨层共享:PyramidInfer

关键约束

  • 不能影响 attention 计算的正确性
  • decode 阶段 KV 不断增长,压缩要 streaming
  • 训练好的 LLM 不能重训
  • 通常要求 tuning-free

代表作 · H2O(2023)· ~500 引 · NeurIPS 2023

Heavy-Hitter Oracle: An Accurate and Efficient KV-Cache Eviction Policy · Zhang et al.(ETH)

核心观察

  • LLM attention 分数服从 重尾分布
  • 只有少数 token 累计 attention 很高
  • 这些叫 "Heavy Hitter"(累计重要 token)
  • 其他 token 可丢弃

方案

  • 累计每个 token 历史上的 attention 分数
  • 每生成 N 个 token,触发 eviction
  • 保留累计分数最高的 top K 个 token
  • 加 recency bias(新 token 暂时豁免)

效果

  • OPT-6.7B: 缓存 20%,PPL 几乎不变
  • LongBench / StreamEval SOTA
  • cache budget 50% 时精度接近 baseline
启示:"累计 attention"作为重要度指标 = KV 压缩的开创性思路。Scissorhands / Scissorhands++ 都用类似思想。

代表作 · Scissorhands(2023)· ~300 引 · ACL 2024

Sparse Attention via Persistent/Compacted Context · Liu et al.(Microsoft)

核心思想

  • 在 PPL 阶段识别"关键 phase"
  • 在关键 phase 出现的 token,后续保留
  • 非关键 phase 出现的 token,可以丢弃

三步法

  • ① 探测:1-shot,找重要 phase
  • ② 筛选:标记重要 token 子集
  • ③ 紧凑:推理时只保留这些 token

效果

  • LLaMA-7B 30% cache → 等同 100%
  • 支持 100K+ context 推理
  • vLLM / SGLang 已集成类似思路
与 H2O 对比:H2O 关注"累计重要度",Scissorhands 关注"phase-level 重要度"。两种思路可结合。

代表作 · StreamingLLM(2023)· ~800 引 · ICLR 2024

Efficient Streaming Language Models with Attention Sinks · Xiao et al.(MIT + Meta)

关键发现:"Attention Sink"

  • softmax 总和 = 1,需要"占位" token
  • 初始几个 token 总是获得 不必要的高 attention
  • 不是它们内容重要,是 softmax 强迫 attention 有去处
  • 这些占位 token 叫 "attention sink"

方案

  • 永远保留:前 N 个(sink) + 最近 M 个(window)
  • 中间 token 全部丢弃
  • 无需训练,无需额外参数
  • Llama-2 7B + 4K sink + 1K window 跑 4M+ 上下文

影响

  • 引 ~800,KV 压缩领域最经典
  • vLLM, SGLang 集成 默认推荐
  • 启发了 FastGen / H2O+ 等组合方案
启示:softmax 的"占位效应"是 attention 计算的内在属性,而非 bug。理解这点让"滑动窗口 + 锚点"成为通用范式。

代表作 · FastGen(2023)· ~200 引

Efficient Generation with Adaptive-Compression KV-Cache · Ge et al.(Microsoft)

核心思想

  • 不同 attention head 偏好 不同压缩策略
  • 让模型自己学(head-specific)选哪种策略

支持的策略

  • ① Heavy Hitter(H2O 思路)
  • ② Window(滑动窗口)
  • ③ Attention Sink(StreamingLLM)
  • 每个 head 选一个,组合压缩

效果

  • OPT-175B 40% 显存 节省
  • 延迟降低 2.1×
  • 零质量损失
启示:"head 自适应压缩策略"让 KV 压缩从"一刀切"变成"按需压缩"。后续工作(SnapKV, PyramidInfer)都继承这一思想。

代表作 · KIVI(2024)· ~400 引 · ICLR 2024

2-bit KV Cache Quantization with Tuning-free · Liu et al.

核心观察

  • Key 在 per-channel 维度有 outlier
  • Value 在 per-token 维度有 outlier
  • 两种分布特征 完全不同

方案

  • Key → per-channel 2-bit 量化
  • Value → per-token 2-bit 量化
  • Llama-2 7B + 2-bit KV → 6.7× 显存
  • PPL 损失 < 0.1

贡献

  • 首个 tuning-free 2-bit KV 量化
  • 可与 H2O / StreamingLLM 组合
  • 被 vLLM、TensorRT-LLM 集成
启示:"K 和 V 需不同量化策略" 是 KIVI 的关键发现。KVQuant(2024) / ZipCache(2024) 都继承。

前沿 · KVQuant(2024)+ PyramidInfer(2024)+ ShadowKV(2024)

KV 压缩的"高阶"组合方案

KVQuant(Hooper et al. NeurIPS 2024)

NVIDIA

  • 精度敏感 残差 + 分离 outlier
  • Key sub-channel 量化
  • Llama-3 8B 3-bit KV 仍高精度
  • 配合 KV 预量化训练

PyramidInfer(Yang et al. ASPLOS 2024)

CMU

  • 观察:不同 layer 重要性不同
  • 浅层 → 长 KV(细粒度)
  • 深层 → 短 KV(粗粒度)
  • 如金字塔:上窄下宽

ShadowKV(Sun et al. 2024)

ByteDance

  • 把 低精度 KV 留在 GPU
  • 把 完整 KV 卸到 CPU/SSD
  • 需要时按需加载
  • Llama-3 70B 128K context 单卡可跑
2024-2025 趋势:"稀疏 + 量化 + 分层 + 跨设备"四种思路组合,让 KV 压缩从"算法"演变为"系统优化"。

SnapKV(2024)+ Quest(2024)+ 后续

基于"查询感知"的 KV 压缩

SnapKV(Li et al. ACL 2025)

SnapKV: Locally Important Layers

  • 核心 insight:query 知道 它在找什么
  • 用 clustering + attention 分数找重要 KV
  • 每个 query 选择 top-K KV 块
  • Llama-3 8B + 1M context 6.6× 加速
  • Code Llama 34B 8.3× 加速

Quest(Tang et al. ICML 2024)

Query-Aware Sparsity for KV

  • 在 每个 decode 步骤 动态选 KV 块
  • 用 query × key norm 预估 重要性
  • 无需 full attention 计算
  • Llama-7B 2.4× 加速,PPL 不变

2024-2025 综合趋势

· "查询感知"(query-aware)成为 KV 压缩的新范式 · StreamingLLM + SnapKV = 静态结构 + 动态细节 · SGLang / vLLM / TensorRT-LLM 都内置多种 KV 压缩策略 · 评估:RULER(2024)成为长上下文 KV 压缩的事实标准评测

代表作 · LLMLingua(2023)· ~700 引 · ACL 2023

Prompt Compression via Linguistic Information · Jiang et al.(Microsoft)

核心思想

  • 用 小模型(如 GPT-2 / BERT) 评估 token 信息量
  • 丢弃 低信息 token(停用词、重复、模板)
  • 保留 高信息 token(实体、关键动作)

关键算法

  • ① 困惑度差:PPL 升幅小的 token 重要
  • ② 条件熵:在上下文的条件信息
  • ③ token 分类:粗粒度保留(名词/动词)
  • ④ 预算分配:动态分配到每段

效果

  • 20× 压缩率,精度 几乎不变
  • 支持 QA / 摘要 / CoT 多任务
  • 代码已开源,被广泛使用
  • LongLLMLingua(2024)扩展到长 prompt
启示:"小模型评估 token 重要度"是 prompt 压缩的"零成本"方案。LLM 不需要重训,小模型跑得快。

代表作 · LLMLingua-2(2024)· ~300 引 · ACL 2024

Prompt Compression via Token Classification · Pan et al.(Microsoft)

改进点

  • 把 prompt 压缩视为 序列标注 任务
  • 训练一个 分类器:每个 token 判"保/删"
  • 更 准确 + 更快

训练数据

  • 用 GPT-4 做 teacher labeling
  • 训练 BERT-style 分类器
  • 训练数据从公开 QA 数据集采样

效果

  • 20× 压缩,精度 优于 LLMLingua
  • 推理 3-5× 更快
  • 对 多语言 也支持
  • 工业部署友好
启示:从"启发式(LLMLingua)"到"学习式(LLMLingua-2)"是 prompt 压缩的范式升级。后续 SelectiveContext、Compress-and-Prompt 都走"小分类器"路线。

Selective Context(2023)+ CompAct(2024)+ 其它

Prompt 压缩的多个变体

Selective Context(Yeo et al. ACL 2024)

基于 self-information

  • 用 自信息(-log p)衡量 token 重要度
  • 小模型(Llama-7B)做 evaluator
  • 支持 phrase-level 压缩
  • 4× 压缩,QA 任务几乎不掉点

Compress-and-Prompt

先生成压缩版,再 prompt

  • 用 LLM 生成 摘要 作为新 prompt
  • 两阶段:压缩 + 提问
  • 适合 RAG 场景
  • 依赖 LLM 摘要质量

CompAct(2024)

任务感知压缩

  • 压缩时考虑 下游任务
  • 训练 compression policy
  • 比通用压缩精度高 5-10%

2024-2025 趋势

· "压缩 + RAG" 联合优化(检索时只返回相关 chunk,不再额外压缩)· AdaComp(2024)任务自适应压缩 · ChunkedLLM(2024)分块压缩 · xRAG(2024)把文档压缩成 1 个 embedding · MemoRAG(2024)memory-based 检索

代表作 · ICAE(2024)· ~150 引 · NeurIPS 2024

In-Context Auto-Encoders · Ge et al.(Microsoft)

核心思想

  • 训练一个 autoencoder 把长 context 压缩成 N 个 memory token
  • 把 memory token 拼到 prompt 前面
  • LLM 推理时,只需关注 少量 memory

训练方法

  • Encoder:LoRA 适配 LLaMA
  • Decoder:重训,确保 LLM 能从 memory 恢复信息
  • 目标:memory 包含原 context 的 全部信息

效果

  • 4× 压缩 几乎无质量损失
  • 8× 压缩 < 1% 掉点
  • 在 LLaMA-2 7B 验证
  • 训练成本相对低
启示:"把 context 编码为少量 memory token"是 prompt 压缩的"端到端可学习"范式。AutoCompressor(2023)/Gist Token(2023)/ChunkedLLM(2024)都是这个思路。

AutoCompressor(2023)+ LongLLMLingua(2024)

学习式压缩 + 超长 prompt 压缩

AutoCompressor(Chevalier et al. NeurIPS 2023)

Stanford

  • 用 summary token 渐进压缩
  • 每 N 个 token 压缩为 1 个 summary
  • 训练:让 LLM 能从 summary 还原
  • 支持 无限长 context 推理

LongLLMLingua(Jiang et al. ACL 2024)

LLMLingua 长 prompt 版

  • 针对 10K-100K token 的 prompt
  • 改进:动态 question-aware 压缩
  • 用 GPT-4 评分(代替 PPL)
  • 长文档 QA 21× 压缩不掉点

核心对比

· LLMLingua 系列:轻量、小模型评估、tuning-free · ICAE / AutoCompressor:需要训练、但压缩率更高 · LongLLMLingua:QA 任务专用 · ChunkedLLM:分块独立压缩 · Gist Token:Meta 的"提示词压缩"

代表作 · YaRN(2023)· ~800 引

Yet another RoPE extensioN · Peng et al.(Nous Research)

核心思想

  • RoPE 频率分解:低频 控制长程, 高频 控制短程
  • 对 不同频段 用不同缩放策略
  • 无需训练,只需修改推理时的位置编码

关键技术

  • NTK-by-parts 插值
  • Attention temperature scaling
  • 对 维度 分类:高频/中频/低频
  • 只需 16 token 长文本微调(可选)

效果

  • Llama-7B: 2K → 128K 无损
  • CodeLlama 16K → 64K
  • 无需训练,5 分钟集成
  • 被 Llama-2-Long / Qwen-Long 等采用
启示:RoPE 频段分离是长上下文的关键 insight。高频用线性,低频用 NTK 插值,这是"手术式"扩展。

LongRoPE(2024)+ LongLoRA(2023)+ Landmark(2023)

长上下文三大代表

LongRoPE(Ding et al. 2024)· ~300 引

Microsoft

  • 用 进化搜索 找每维的最佳缩放因子
  • Llama-2 7B 2K → 2M(需 1K step 微调)
  • 非均匀缩放,不同维度不同

LongLoRA(Chen et al. NeurIPS 2023)· ~600 引

CUHK

  • 用 Shifted Sparse Attention 训练
  • 训练 O(n²) → O(n√n)
  • 单卡 24GB 即可微调 100K context
  • 配合 LoRA,资源极少

Landmark Attention(Mohtashami, NeurIPS 2023)

Meta

  • 每个 block 选 landmark token 存 KV
  • 查询只 attend 到 landmark
  • O(n²) → O(nk),k 是 landmark 数
三类思路对比:· 位置编码(YaRN/LongRoPE)改 PE · 训练(LongLoRA)改注意力 · 稀疏(Landmark)改 attention 模式

长上下文评测 · RULER(2024)

RULER: What's the Real Context Size of Your Long-Context Language Models? · Hsieh et al.(NVIDIA)

13 个评测任务

  • Needle-in-Haystack:大海捞针
  • Variable Tracking:变量追踪
  • Multi-hop QA:多跳问答
  • Aggregation:信息聚合
  • Common/Extraction:抽取

关键发现

  • 声称 128K context 的模型,实际 经常只能 4-32K
  • Llama-2-7B 声称 32K → RULER 上 4K 掉 30%
  • Llama-3-8B 128K → RULER 上仍 60%
  • 开源模型 普遍 短于声明

意义

  • 长上下文研究 必须跑 RULER
  • 推动更诚实的 context window 报告
  • LongBench(2024) 中文版补充
启示:"声称的 context window" ≠ "实际有效" 。RULER 让长上下文研究从"自吹"走向"实测"。

长上下文经典论文 · Lost in the Middle(2023)

Liu et al.(Princeton)· ACL 2023· ~1500 引

核心发现

  • LLM 在 长 context 中:
  • · 开头 信息利用最好
  • · 结尾 信息其次
  • · 中间 信息最差(掉 20-30%)

U 型曲线

  • 位置 vs 准确率呈 U 型
  • 长文档 QA 任务尤其明显
  • 即使模型有足够 context 长度

启示

  • · KV 压缩 把重要信息放头/尾
  • · Prompt 压缩 删中间冗余
  • · 位置编码 让中间更稳定
  • · RAG 只返回关键 chunk
为什么是 1500 引?:这篇 2023 的论文揭示 LLM 在长 context 的根本缺陷。所有 KV 压缩、prompt 压缩、长上下文扩展工作,都要解决"Lost in the Middle"问题。

⑤ 投机解码 · Speculative Decoding

核心 idea:小模型草拟 + 大模型验证,并行生成 5-10 个 token,接受率 70-80% 时加速 2-3×。

SpecDec
2-3×
2023 · 经典
Medusa
2-2.5×
2023 · 多 head
EAGLE
2.7-3.5×
2024 · 特征级

核心问题

LLM 自回归推理太慢

  • 每生成 1 个 token 都跑 整个模型
  • memory bandwidth 限制
  • GPU 算力闲置,显存带宽是瓶颈

投机解码原理

  • ① 小模型(Draft)生成 K 个候选 token
  • ② 大模型(Target)1 次 forward 验证
  • ③ 接受正确部分,继续生成
  • ④ 拒绝时大模型重生成

关键指标

  • 接受率 α:小模型预测准确率
  • 草拟长度 K:一次生成几个
  • 加速比:E[1/(1-α)] 当 α < 1
  • 典型:α=0.7, K=5 → 2.5× 加速

代表作 · Medusa(2023)· ~400 引

Medusa: Simple LLM Inference Acceleration Framework with Multiple Decoding Heads · Cai et al.(UCSD + Together AI)

核心思想

  • 不训练 draft model
  • 在 LLM 顶层加 多个 Medusa head
  • 每个 head 预测第 N+1/N+2/N+3 个 token
  • 所有 head 并行 预测

训练

  • 冻结 LLM 主干
  • 只训 Medusa heads (几行 FFN)
  • 训练成本极低
  • 1-2 小时即可

效果

  • Vicuna-13B 2.2× 加速
  • Vicuna-33B 2.3× 加速
  • 代码简单,集成 几行
  • 已被 vLLM / SGLang 集成
启示:"不训 draft model + 多 head 并行"让投机解码变得简单实用。这是工业部署的 首选 方案之一。

代表作 · EAGLE(2024)· ~300 引 · NeurIPS 2024

EAGLE: Extrapolation Algorithm for Greater Language-model Efficiency · Li et al.(复旦 + Microsoft)

改进点

  • 不在 token 空间,改在 特征空间 自回归
  • 用 下一层特征 预测
  • 更 精准 + 接受率更高

训练

  • 1 层 Transformer head
  • 训练数据极少
  • 接受率 0.8+ (vs Medusa 0.7)

效果

  • Llama-2-Chat 70B 2.7× 加速
  • Llama-3-8B-Instruct 3.5× 加速
  • 代码 开源
  • 已被多个推理框架集成
启示:"特征级自回归"比"token 级"信息量更密集,是投机解码的 新范式。EAGLE-2(2024)继续优化到 4× 加速。

  • LLM 端 KV 压缩:H2O / KIVI
  • 两者误差累积,最终掉点严重

技术路径

  • · 联合目标函数:ViT token 重要度 ∝ LLM 关注度
  • · 跨模态 attention 指导 ViT 端剪枝
  • · 端到端训练 vision-projector-LLM
  • · 模态平衡 loss

Idea B · KV 压缩的隐私影响

目标:S&P 2026 / USENIX Security 2026 / TDSC · 难度:中-高 · 时间:9-12 月

问题

  • 压缩后的 KV cache 仍是公开
  • 攻击者能否从 KV 反推 原始 prompt?
  • KV 压缩本身 是否泄露 隐私信息?

攻击面

  • KV Inversion:从压缩 K/V 反推 token
  • KV Embedding Leakage:outlier 位置 = 关键信息
  • Compression Pattern Attack:被丢弃的 token ≠ 隐私
  • Membership Inference:从 KV 模式判断训练样本

防御 + 评估

  • 差分隐私 + KV 压缩(DP-KV)
  • 压缩时加噪(noise-aware quant)
  • 构建 KV 隐私 benchmark
  • 对比 H2O / KIVI / StreamingLLM

为什么能发

· 交叉领域:KV 压缩 × 隐私, S&P 喜欢看新攻击面 · 现有工作(Wei et al. 2023 Q-sniffer)只做 FP, 没做 KV 压缩 · 实用威胁:OpenAI / Anthropic API 的 KV 缓存都是攻击目标

Idea C · 自适应长上下文(动态 context window)

目标:ICML 2026 / NeurIPS 2026 · 难度:中 · 时间:6-9 月

问题

  • LLM context window 固定(8K / 128K)
  • 短 query 时浪费算力
  • 长 query 时不够用
  • 需要 动态 调整

技术路径

  • · 输入长度 预测(LSTM / 轻量模型)
  • · 动态路由:短 → 浅层,长 → 深层 + 稀疏
  • · 位置编码 按 query 自适应
  • · KV 预算 动态分配

实验设计

  • Llama-3 8B / Qwen2.5 7B
  • 多 query 长度(100 / 1K / 10K / 100K)
  • 对比固定 context vs 自适应
  • 评测:RULER + LongBench + 短任务

为什么能发

· 2024-2025 仍空白 · ICML 偏好 自适应 / 动态 方法 · 实用价值:每次 query 节省 30-50% 算力 · 代码基础:YaRN 已有,加 routing 模块即可

Q & A · 3 道思考题

3 道思考题

  1. 为什么 2023 是 token 压缩的"元年"?

    这一年 LLM 出现,长上下文成为刚需,所有 token 优化从"加速 ViT"扩展到"压缩 LLM"。是不是技术准备好了,还是 LLM 倒逼了 token 压缩?两者哪个先?

  2. 投机解码与 KV 压缩,哪个更重要?

    投机解码加速 2-3×,KV 压缩让 1M context 可行。它们针对不同瓶颈,组合使用效果如何?有没有互相干扰的情况?

  3. 长 context 真的有用吗?

    Lost in the Middle 揭示 LLM 在长 context 利用率不高,RULER 揭示声称的 128K 实际只能 4-32K。1M context 是真需求还是营销噱头?
